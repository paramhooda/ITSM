# Architecture

This document records the engineering decisions behind the MSP Service Management Platform: what was chosen, why, and what was deliberately left out.

## 1. Shape of the system

**A modular monolith, deployed as two processes (API + worker) over PostgreSQL and Redis.**

| Concern | Decision | Rationale |
| --- | --- | --- |
| Deployment unit | One container image, two commands (`server`, `worker`) | On-premise MSPs need something an infrastructure team can run, back up and restore. One image, two stateless processes and two stateful services (PostgreSQL, Redis) keeps the operational surface small while allowing horizontal scaling of API and worker replicas independently. |
| Code structure | Modules under `apps/api/src/modules/<name>` (routes + service + schemas), shared core | Clear ownership and boundaries without network hops. Modules communicate via service functions inside the same transaction, which keeps multi-entity operations (ticket + SLA + audit + notification) atomic. If one module ever needs independent scaling (e.g. event ingestion), its queue-based design allows extraction. |
| Language / runtime | TypeScript on Node.js 22 (Fastify 5) | One language across API, workers and UI; large ecosystem for SNMP, SMTP, PDF/CSV; strong typing for a wide domain model. |
| Database | PostgreSQL 16 | System of record for everything. JSONB for configurable fields, native full-text search + trigram indexes for global search, declarative partitioning for high-volume tables, row-level security for tenant isolation. |
| Queue / scheduling | Redis 7 + BullMQ | SLA timers, notification delivery, scheduled reports, discovery runs, event processing, housekeeping. Cron-style repeatable jobs live in the worker; jobs are idempotent and safe to retry. |
| Web UI | React 19 + Vite, served by the API | Single-page app with a focused operational layout. Built into the same image; no separate web server needed. |
| Search | PostgreSQL FTS (`tsvector` generated columns) + `pg_trgm` | Adequate for millions of tickets with GIN indexes; avoids operating a second search cluster. A `SearchProvider` abstraction (`modules/search`) allows OpenSearch/Meilisearch later. |
| Attachments | Filesystem volume via a `StorageDriver` interface | S3-compatible storage can be added without touching callers. |
| AI | Provider abstraction: Anthropic, OpenAI-compatible (on-prem models), or none | The assistant uses *tools* that call the same service layer with the caller's authorization context. AI can never see or do more than the user. |

Explicitly **not** chosen: microservices, Kafka, Elasticsearch, Kubernetes-only deployment, a separate BFF. None of them are needed to reach the target scale (1,000+ customers, 1,000+ tickets/day, millions of historical tickets) and each would add operational cost for an on-premise MSP.

## 2. Tenant isolation (customer data boundary)

Three layers, each sufficient on its own:

1. **Principal resolution.** Every request resolves a `Principal` with a `customerScope`: `'all'` (holds `tenant:all`) or an explicit list of customer IDs derived from customer-scoped role assignments, explicit access grants and team-to-customer assignments. Customer (portal) users always resolve to exactly their own customer.
2. **Application checks.** Services call `ctx.requireCustomer(id)` before touching a customer entity and `ctx.require(permission, customerId)` for actions.
3. **PostgreSQL row-level security.** Every request runs inside a transaction that sets `app.user_id`, `app.all_customers` and `app.customer_ids`. All tables that carry `customer_id` have a `FORCE ROW LEVEL SECURITY` policy evaluated through STABLE functions (`app_customer_ids()`), so even a bug in application code cannot leak another customer's rows. The runtime database role is a non-superuser without `BYPASSRLS`; migrations use the owner role.

Background jobs run with the system context (`app.all_customers = true`) and must pass explicit customer IDs into every notification/report they produce.

Rows with `customer_id IS NULL` are *shared* (global knowledge articles, platform-wide catalog items) and are visible to all.

## 3. Authorization model

* **Permissions** are flat strings (`tickets:resolve`, `contracts:manage`, `portal:approve`...), catalogued in `packages/shared/src/permissions.ts`.
* **Roles** bundle permissions. Seventeen system roles ship by default (Administrator, NOC Engineer, SOC Analyst, Service Manager, Account Manager, CMDB Administrator, Contract Administrator, Management, Auditor, Customer Administrator, Customer User, Customer approver...). Administrators can create more. `seedRoles` creates a new `SYSTEM_ROLES` entry on the next start and never removes a permission an installation already holds.
* **Role assignments** are global or scoped to one customer. A user may be *Engineer* globally and *Service Manager* for one strategic customer.
* **Visibility** (which customers) is separate from **capability** (which actions). `tenant:all` grants MSP-wide visibility; otherwise visibility is the union of scoped assignments, explicit grants and team assignments.
* The three initial categories map to roles: Customer → `customer_user`/`customer_admin`, Engineer → `engineer`/`noc_engineer`/..., Admin → `admin`. A customer user holds one base role; `customer_approver` (`portal:access`, `portal:approve`) is added beside it when the organisation's administrator switches *Customer approver* on in the portal (or staff assign it in the user editor): `portal/service.ts` always writes the full list (base role + optional approver) in one `setUserRoles` call, because `setUserRoles` deletes and re-inserts, and reports `canApprove` from either role on `safeUser` and on `GET /customers/:id/users`.

## 4. Domain model (summary)

```
Customer ─┬─ Sites ─┬─ Assets ──── CIs ──┬── CI Relationships
          │         └─ Contacts          ├── Tickets (incident/request/problem/change)
          │                              │    └── Known errors (problem_details)
          │                              └── Software installations (per CI / asset / user) ── Software catalogue (shared titles)
          ├─ Contracts ─┬─ Covered services (→ Service catalog) ─ SLA policy override
          │             ├─ Covered sites
          │             ├─ Entitlements ── Consumptions (field visits, time entries, PM visits)
          │             ├─ Scope items (in/out of scope definitions)
          │             └─ Software licences (seats, metric, term, cost, proof of purchase)
          ├─ Field visits ── parts, notes, acknowledgement
          ├─ PM programs ── occurrences
          ├─ Knowledge (customer-specific) / shared knowledge
          └─ Report schedules / runs
```

* **Tickets** are one table with a `type` discriminator (`incident`, `request`, `problem`, `change`) plus extension tables (`problem_details`, `change_details`) and `form_data` for catalog request forms. Shared behaviour (comments, activities, links, SLAs, tasks, time, attachments, watchers) is implemented once. `problem_details` also carries the known error database: status, fix change, customer-facing wording and portal publication; the portal reads only the customer fields.
* **The ticket lifecycle** is one transition, `changeStatusCore` in `modules/tickets/status.ts`, used by the status endpoint, the convenience actions, the approvals service, the CAB, the auto-close job, the portal's confirm, the customer-reply hook and the composer's reply-and-wait (`addComment.then`, staff with `tickets:update`, a pending status only: resolving, closing, cancelling and reopening keep their own rules). It applies the transition profile by status category (`TRANSITION_PROFILES` and `transitionsFor` in `packages/shared/src/constants.ts`, chosen by the setting `tickets.transition_rules`; `TICKET_TRANSITIONS` stays exported as the `strict` table; the web reads the same profile for the status menu and the board drops), the reason of a wait when the setting requires one (a pending status whose option metadata is not `wait: false`; `isWait` in `tickets/common.ts`; `reasonRequired` in `tickets/settings.ts`) and the party waited on (`WAITING_ON`: customer, vendor, change, agreement, internal; `waitingOnLabels` gives the staff and the customer wording from one table). The pending block on `tickets` (`pending_reason`, `pending_waiting_on`, `pending_expected_at`, `pending_reference`, `pending_reason_visible`, `pending_set_by`, `pending_set_at`; migration `0024_pending_and_approvals`, which also adds `requested_by`, `purpose`, `due_at` and `reminded_at` on `approvals` and the partial indexes `tickets (pending_waiting_on)` and `approvals (due_at) WHERE status = 'pending'`) is written on every entry into a wait and cleared on every exit. The timeline gets two `pending` rows (a customer-visible one in the customer's words that carries the reason only when it was shown to them, a staff one with everything) and the `status` row is internal when an internal hold is on either side; `getTicket` returns the staff block, or for a customer user exactly `{ waitingOn, waitingOnLabel, reason | null, expectedAt }` (null for an internal hold). The lifecycle rules an administrator can change are read by `loadLifecycleSettings` in `modules/tickets/settings.ts` (six keys, `tickets.transition_rules`, `tickets.pending_reason_required`, `tickets.cancel_comment_required`, `tickets.reopen_comment_required`, `approvals.rejected_change`, `approvals.rejection_note_required`; one select, every unknown value coerced to its default; the module imports nothing from the ticket services) and passed through `StatusChangeOptions.settings`; `StatusChangeOptions.flowSet` is the one exemption from the profile, an explicit flag passed by the approvals service's own moves and the CAB's no-step rejection and never inferred from the action or the status keys. The clock rule is a term of the SLA policy: `sla_policies.pause_metrics` and `pause_waiting_on` (migration `0025_sla_pause_policy`, both `text[]` with the shipped rule as default; `sla_policies` carries no `customer_id` and no row-level policy by design, because `applySlas` runs inside a portal user's transaction when a customer raises a ticket), read by one module, `modules/sla/pause.ts` (`PauseRule`, `loadPauseRule`, `waitPauses`, `metricPauses`, `pauseWords`), which the engine, `getTicket().pauseRule` (staff only), the assistant's previews and the dialogs' sentences all come through, so no file names a metric or a party as a pausing constant. The SLA engine (`modules/sla/engine.ts`) pauses the policy's clocks for the policy's parties on entry, on a wait-to-wait move, on reopen and on creation alike; the one named pair left is `REOPEN_RESTART_METRICS` (resolution and restoration): a reopen restarts the clocks whose timestamps it clears, whatever the policy pauses, and the policy governs only whether they start paused; `resumeFromPending` ends a wait (a customer reply only for a customer reply wait with no approval pending; an approval through `AFTER_APPROVAL_KEY`). `ticket.pending` and `ticket.resumed` are sent for waits the customer may know about, `ticket.status_changed` goes `staffOnly` for internal holds. The seed applies `OPTION_UPGRADES` and `TICKET_UPGRADES` (`seed/upgrades.ts`) on every start, idempotently, so an upgraded installation keeps its waiting tickets. "Waiting on the customer" is one predicate, open and `pending_waiting_on = 'customer'`, read by the list stats tile (`awaitingCustomer`), `amcTotals` and the AMC queue, the handover digest, Grady's `awaiting_customer` bucket, the portal list and stats, `customer().tickets.waitingOnYou` and the brief's doors; its list key is `waitingOn` (a comma list of `WAITING_ON` on the staff list and in `PASS_THROUGH`; `TicketListLink.waitingOn`; `z.literal('customer')` on the portal routes, the only value `portalTicketListQuery` emits and `query_tickets` accepts from a portal user), and `portalStatusOf` (`modules/portal/service.ts`) maps an internal hold to the type's working status on every portal row.
* **Approvals** (`modules/tickets/approvals.ts`) are a lifecycle step on every ticket type. `approvals` rows carry the step (`step`, `step_name`, the addressee as `approver_user_id`, `approver_role_key` or `approver_team_id`), `requested_by`, `purpose`, `due_at`, `reminded_at`, the decision (`decided_by`, `decided_at`, `comment`) and a status among pending, waiting, approved, rejected, skipped, superseded, cancelled and expired; `tickets.approval_status` reads not_required, pending, approved, rejected, withdrawn or expired. `planApproval` validates a request (an open ticket, an assessed change, one of a workflow or an approver: the organisation's approvers as kind `customer` (alias `customer_admin`; the organisation step keeps `approver_role_key = customer_admin`, `ORG_APPROVERS_KEY` in `tickets/common.ts`, read everywhere as the holders of `portal:approve` for the customer; a workflow step of type `role` on any customer role key is normalised to it in `addressee`, labelled "the approvers of <customer>") or one of them by id through `requireCustomerApprover` (active, `user_type = customer`, `users.customer_id = ticket.customer_id`, a role scoped to that customer or unscoped whose permissions include `portal:approve`; one refusal message), a user, a role (a customer role means the organisation step), a team; a rejected ticket plans a resubmission, `resubmits: true`, which `requestApproval` performs first through `changeStatusCore` as a flow-set reopen into `REJECTED_RETURN_KEY[type] ?? REOPEN_KEY[type]`, Draft for a change, with the comment "Resubmitted for approval") and is shared with the assistant's preview; `startApproval` writes one row per step, resolves the awaiting status without swallowing a missing one, and moves the ticket through `changeStatusCore` with the purpose as the reason and `partyOf(first step)` as the party, so the engine pauses only for a customer addressee; `decide` sets `approval_status` before any status change it triggers, re-points the party pending → pending when it releases the next step, and applies `AFTER_APPROVAL_KEY` or `afterRejection(type, settings)` (both in `status.ts`; `return` for a change under the default `approvals.rejected_change`, mirrored on the `working` branch through `resumeFromPending(…, { to: REJECTED_RETURN_KEY.change })` only while the ticket is in the approval wait, `rejected` otherwise; `AFTER_REJECTION` stays as the `rejected` profile's table) with the rejection note required per `rejectionNoteRequired(settings, isCustomerUser)`; `changes/service.ts` applies the same setting when the board rejects a change with no step pending, flow-set (a change already in Draft keeps its status but still takes the rejected approval status and the audit entry), and no longer swallows a missing status; `withdraw`, `cancelPendingApprovals` (in `status.ts`, on resolve and cancel) and the expiry queue their approver notifications before the rows leave pending, because `resolveRecipients.approvers` reads pending rows; the organisation step resolves its recipients through `usersWithPermission(tx, 'portal:approve', customerId)` in `notify.ts` (users × user_roles × roles × role_permissions, fenced on `users.user_type = 'customer'`, `users.customer_id = customerId`, an active user and an assignment unscoped or scoped to that customer), every other role key through `usersWithRoles`. `isEligible` for a customer user on the organisation step is `ctx.user.customerId === approval.customerId && ctx.can('portal:approve', approval.customerId)`, and `listMine` adds the organisation step for the user's own organisation only when they hold the permission for it, so an approver assignment of another organisation (even an unscoped one written by hand) never reaches a ticket that is not theirs. The job `approval-reminders` (`sla` queue, hourly, `jobs/processors/approvals.ts`) runs `remindAndExpire` one transaction per ticket under the `approvals.*` settings. The six `approval.*` events are type-neutral, in the `approvals` notification category, with email and WhatsApp templates and seeded rules; every emission passes `recipientFallback` and the three channels. The portal (`getPortalTicket().approvals`, `GET /portal/approvals`) lists only steps addressed to the organisation; the decision row of an internal step is staff-only, and so are its notifications while the outcome is a return to work (`outcomeStaysInternal`: a request or change ending as Rejected, a change moving to Approved, is told to the requester). A decision, a withdrawal and an expiry resume only the approval wait (`inApprovalWait`); a withdrawal resumes through the `withdrawal` trigger (silent, the reason never posted as a reply); a released step is pending since the previous step's decision (`pendingSince`) and names the requester as the actor of its `approval.requested` (`NotifyExtra.actorName`). Plain-text notification output (email subjects, WhatsApp bodies, the report email subject) renders through `renderText` in `lib/templates.ts`, unescaped; the HTML body keeps `render`.
* **Statuses, categories, priorities, sources, codes, contract types, scope headers, entitlement types, asset categories, visit types, CI types and relationship types are data** (`config_options`, `ci_types`, `ci_relationship_types`), seeded with sensible NOC/SOC/AMC defaults and editable in Administration. Every status maps to a *status category* (`new/open/pending/resolved/closed/cancelled`) so SLA logic and reports work with any custom status.
* **Scope** is a classification (`in_scope`, `out_of_scope`, `unknown`) computed from the customer's contracts, services, sites, ticket category and CI type and recorded on the ticket. It is informational: nothing in the ticket workflow is blocked by scope.
* **SLA**: policies contain targets per ticket type × priority × metric (acknowledgement, response, restoration, resolution). Each ticket gets one `ticket_slas` row per applicable metric with the calendar snapshot used, `due_at`, pause accounting and an event trail. Policy selection order: catalog item → contract service override → contract → service default → platform default.
* **Assets vs CIs**: assets hold the financial/lifecycle view (purchase, warranty, AMC, location, ownership); CIs hold the operational/relationship view. They may link 1:1 but either can exist alone.
* **Changes**: `change_details` extends a change ticket (window, plans, risk answers and score, template, CAB meeting); `change_templates` (standard changes), `change_risk_questions`, `change_blackout_windows` (global or per customer) and `cab_meetings` / `cab_meeting_items` are the change-management tables; conflicts are computed, never stored (an activity records them); `change-window-reminder` runs hourly on the `sla` queue. The three definition tables carry no customer column and are fenced to staff by an explicit row-level policy; the portal reads planned changes from `tickets` and `change_details` only.
* **Satisfaction surveys**: one `ticket_surveys` row per ticket (the recipient, the hashed and encrypted token behind the email links, the rating, the comment, the channel and a snapshot of the engineer and team at the time), `survey_configs` overrides per customer or contract over the `surveys.*` settings; `tickets.csat_rating` denormalises the answer for lists and filters. CSAT figures are computed live from the surveys table.
* **Software**: a shared catalogue of titles (`software_products`, no customer); installations (`software_installations`, on a CI, an asset, a host name or a user) and licences (`software_licences`, with a self-reference to the licence that continues a renewed one) belong to one customer; the compliance position is computed live (never stored) from live hosts and licences in term; `software_notifications` records the once-only notification milestones.
* **Task boards** are views over tickets and `ticket_tasks` (lanes by status or assignee, scoped by person, team or engineer); every move runs the ticket's own status, assignment and task transitions. Only `board_notes` (one person's sticky notes, per-user row-level security) is new; board layout lives in `users.preferences`.
* **Custom report definitions** (`report_definitions`) are MSP artefacts: an entity key and a whitelisted specification (columns, filters, grouping, aggregates, sort, period field) compiled into parameterised SQL by `modules/reports/builder/compile.ts` over the field catalogue; they run through the same executor, renderers and schedules as built-in definitions under the caller's row-level security context, carry `scope_customer_id` (not `customer_id`) so the tenant policy does not apply to the definition itself, and an explicit policy lets staff read every row and portal users only the rows published for their organisation.
* **Notification preferences**: `notification_categories` holds the administrator's default and lock per category and channel (fifteen rows seeded from the shared catalogue in `packages/shared`, readable by everyone and written by staff under an explicit policy); a person's choices sit in `users.preferences.notifications` (only the cells they set); `queueNotification` applies rule ∩ person ∩ opt-in for every recipient with an account and never vetoes in-app; `phone_verifications` (hashed one-time codes, per-user row-level security) and `users.whatsapp_verified_at` with the partial unique index `users_whatsapp_verified_phone_idx` record proof of ownership of a mobile number (one account per verified number).
* **WhatsApp inbound** (`whatsapp_inbound`): every message sent to the business number, deduplicated by Meta's message id, resolved to a person, with the outcome and the reply's outbox row; staff-only under an explicit policy, purged with the outbox. The chat flag itself is `users.preferences.whatsapp.assistant`.

## 5. Scale and reliability

* **Indexes** on every foreign key used in filters, composite `(customer_id, created_at)` for tenant time-series, GIN on search vectors and trigram columns.
* **Partitioning** by month for `audit_log` and `integration_events`; a maintenance job creates partitions ahead and drops expired ones per retention settings. Tickets stay unpartitioned (indexes suffice into the tens of millions); the path to partition by `created_at` is documented in `OPERATIONS.md`.
* **Dashboards** are pages with explicit scope. `GET /dashboards/overview` (`modules/dashboards/overview.ts`) is the Overview every staff member lands on: `me` (the shift running now from the handover shifts, assigned, due today, approvals, breached on my tickets, my queue by type), the announcements aimed at staff, `upcoming` (visits, maintenance occurrences, CAB meetings and change windows today and tomorrow, each under its own permission or the person's own work), `desk` (only with `tickets:read`: open, breached, at risk, unassigned, resolved and opened in the period with deltas, the daily series, open by type, the five-bucket ageing, the arrivals heatmap, who carries the load by team, engineer, service, customer and category, responsiveness by priority, change outcomes), `strips.noc/soc/amc` (each only with its dashboard permission) and `management` (only with `dashboards:management`: needs attention, expiring contracts, entitlement alerts, CSAT). The strips are computed by `modules/dashboards/totals.ts` (`nocTotals`, `socTotals`, `amcTotals`), the same functions the dedicated NOC, SOC and AMC dashboards read their tiles from, so a strip number equals the tile it links to; the NOC takes a `teamId` filter that every one of its panels and links carries. `modules/reports/analytics.ts` serves both the report documents and the dashboards: its `Scope` takes `domains` and `teamId`, its breakdown and responsiveness rows carry the record id behind them, and `backlogAgeing` cuts its buckets at exact instants and returns the created window of each bar; `arrivalsWeek` in `dashboards/common.ts` counts each day-and-hour cell over its own exact window so a cell drills down to the tickets it counted. The management dashboard's charts and deltas still read `metric_rollups_daily` (computed nightly per customer) plus a live computation for "today"; every number that links is counted live under the caller's fences, never summed from a series. The dashboards, the ticket list and its tiles, the task boards, the customer overview, the briefings and the reports spell "breached" and "at risk" through one helper, `modules/sla/predicates.ts` (the engine flag, and a running clock the engine has warned on). SLA compliance is one helper as well, `modules/sla/compliance.ts` (`resolutionCompliance`, `resolutionComplianceByCustomer`, `resolutionComplianceByPriority`): resolution clocks that ended in a window of whole UTC days under a leading-`AND` fence (met by `completed_at`, breached by `breached_at`, open tickets included, met over met plus breached to one decimal, `null` when nothing ended), read by the Overview (`desk.sla`), the management block and its `needsAttention` rows (`attentionByCustomer`), the NOC, SOC, AMC and engineer dashboards (`sla`), `customer()` (with `byPriority`), `portalSla()` (`resolution`), the customers overview (`slaCompliance30d`, `slaByCustomer`, `slaWindow`), the customer record (`sla30d` with its `period`), `GET /sla/compliance` (`complianceOverview` in `sla/policies.ts`: `resolution` and `period` beside the policy totals; a customer principal is pinned to their own organisation), the service manager briefing's headline and the assistant's `dashboard_kpis` and `sla_compliance` facts; the reports and the policy screens keep `slaCompliance()` (clocks started in the period, every metric) and say so. The thresholds live in `packages/shared/src/sla.ts` (`SLA_COMPLIANCE_TARGET`, `SLA_COMPLIANCE_WARNING`, `complianceTone`), imported by the web and the report theme alike. The ticket list (staff and portal) accepts `slaOutcome=met|breached` with `slaEndedFrom/To` (an `EXISTS` on `ticket_slas` for the resolution clock, the whole-day cut; the window without the outcome is a 422 from `buildWhere`, shared by `/tickets`, `/tickets/stats`, `/portal/tickets` and `/portal/tickets/stats`), the keys travel in `ticketLinks.ts` and the portal-safe set, and migration `0023_sla_outcome_indexes` adds the date-leading partial indexes `ticket_slas (completed_at)`, `ticket_slas (breached_at)` and `tickets (resolved_at)` the helper and the doors scan. Dashboard numbers link to the ticket list through `packages/shared/src/ticketLinks.ts` (now with `siteId`), the chart palette the documents and the dashboards share lives in `packages/shared/src/palette.ts`, and `apps/api/test/dashboards-consistency.test.ts` holds every linking number of the Overview and the dedicated dashboards (tiles, donut slices, ageing bars, heatmap cells, breakdown rows, strips) to the list's own count, as an administrator, a NOC manager without security access and an engineer, with and without a customer scope. The customer portal's list reads the same vocabulary: `GET /portal/tickets` and `GET /portal/tickets/stats` (`modules/portal/service.ts`: `portalListParams`, `countPortalTickets`, `portalTicketStats`) accept the staff list keys that are safe for a customer (status category and id, priority, site, service, SLA state, created and resolved ranges, `csat=pending`), keep the portal's own `status` chip and `priority` key as aliases, pin the organisation through `resolvePortalCustomer` and strip every staff-only key at the route schema; the stats strip `csat` as a tile key as well (`ticketStats` takes a `tileKeys` option), `GET /portal/me` reads its counts from the same function, "to rate" is one predicate (`modules/surveys/figures.ts` `surveyPendingCond`: a live pending survey on a ticket in the resolved or closed category) shared by the list, the stats, the surveys page and the customer dashboard, links into the portal are built with `portalTicketListPath` (the portal-safe key set `PORTAL_TICKET_LINK_KEYS`), and the guard test counts the portal home's doors as a portal principal through `countPortalTickets`. `GET /dashboards/customer?days=&siteId=` (`dashboards/service.ts customer()`, the portal home's payload and the staff preview of one customer) is built on the Overview's recipe: a leading-`AND` fence of the organisation, the staff security condition and an optional site (validated as one of the customer's sites), one live statement for the tiles, `byType` and `byPriority` with their breached share, `bySite` and `byService` through `openLoad` (the `site` dimension), the daily series through the exported `deskSeries` (buckets and window pinned to UTC days so a bar reproduces on the list's cut), `backlogAgeing` and `responsiveness` with the site in their `Scope`, the customer-audience announcements, and an `upcoming` block whose four counts come from one predicate each in `modules/portal/upcoming.ts` (`upcomingVisitCond`, `upcomingOccurrenceCond`, `plannedChangeBuckets`, the approvals service), the same predicates `portalMaintenance`, `portalPlannedChanges` and `me().counts` use; `majorOpen` is `null` for a portal principal. The web page is `pages/portal/PortalHomePage.tsx` on `DashboardFrame` (`strip={null}`, `scope="none"`, `sites`) with `components/dashboards/CustomerDashboard.tsx` as its body.
* **Transactions per request** keep multi-table changes atomic; the audit record is part of the same transaction.
* **Outbox pattern** for notifications: emails are written to `notification_outbox` inside the business transaction and delivered by the worker with retries. Nothing is sent for a rolled-back operation. The `survey-sweep` job (`notifications` queue, hourly) sends the one reminder for unanswered satisfaction surveys and marks the expired ones.
* **Task boards** read `ticket_tasks` through the `(assignee_id, status)` and `(team_id, status)` indexes and cap the cards at `boards.card_limit` with exact lane counts from one grouped query; the nightly `board-notes-purge` job (`maintenance` queue) removes done sticky notes past `boards.note_retention_days`.
* **Software** positions come from two grouped queries (installations on live hosts, licences in term) joined in memory per customer and title; the `software-daily` job (`maintenance` queue, 06:30) sends the licence expiry and over-deployment notifications once per milestone.
* **Report documents** are rendered server-side (SVG charts, the embedded wordmark and typeface, no browser script) and printed by one Chromium process at a time; a compared report runs its definition twice inside one transaction, the narrative phrasing is the only model call and runs between the report's two transactions, and the file is stored in the second.
* **Idempotent jobs** with Redis-backed schedulers; API replicas can start concurrently (migrations use an advisory lock).
* **Health endpoint** `/api/health`, structured JSON logs, request IDs, graceful shutdown.
* Backups: PostgreSQL base backups + WAL (see `OPERATIONS.md`); attachments volume snapshot; Redis is reconstructible (jobs are re-derived from the database on worker start).

## 6. Integration model

PRTG and FortiSIEM are modelled as **integrations** with an API key, a customer mapping and rules. Events arrive at `/api/integrations/:id/events` (generic JSON) or the PRTG/FortiSIEM-specific webhook adapters, are stored in `integration_events`, correlated to a customer and CI (by monitoring reference, hostname or IP) and, if `auto_create_tickets` is enabled, become incidents through the *same* ticket service used by the UI (SLA, assignment rules, notifications included). Deduplication uses the external event ID and a configurable window. Adapters are small translation functions; adding Zabbix, email ingestion or an EDR is a new adapter, not a redesign.

Discovery follows the same pattern: `discovery_sources` of a given `source_type` produce `discovery_findings` which are reconciled into CIs (automatically or after review).

## 7. AI model

* `lib/ai/provider.ts` defines `AiProvider.chat(messages, tools)`; implementations exist for Anthropic and OpenAI-compatible endpoints. With `AI_PROVIDER=none`, conversational features are hidden and rule-based assistance (similar incidents by full-text similarity, knowledge suggestions, priority from the impact/urgency matrix) still works.
* The assistant (`modules/ai/`) exposes a registry of **tools** (`tools/`, 159 of them across every module) that call module services with the caller's `Ctx`, so authorization and tenant isolation apply identically to AI and UI actions. The prompt is assembled from fixed sections (`prompt/`: identity, rules, style, skill playbooks in a cacheable stable block; operating context and capabilities in a volatile block). Toolsets (`toolsets.ts`) keep each model call small and are enabled by the page, a keyword router, the skill or the model itself. A chat turn (`service.ts`) runs the model outside any transaction and each tool call in its own short transaction; actions are proposed with a preview and executed exactly once on confirmation. `POST /ai/chat` answers JSON or a server-sent event stream; `admin.ts` serves the control page. The assistant has a second entry point: the WhatsApp webhook feeds an `ai`-queue job (`modules/whatsapp/`) that runs the same `chatTurn` under the linked person's principal with `channel: 'whatsapp'`, renders the reply as WhatsApp text and records it in the outbox. The application map (`packages/shared/appmap.ts`) describes every page for the guide, validated navigation and page-aware toolsets.
* Recommendations (classification, priority, assignment, similar incidents, KB) are stored as `ai_suggestions` and shown as proposals; a human accepts or rejects them. No silent operational decisions.
* Drafting features (triage, resolution notes, handover notes, briefings, known-error wording, report builder suggestions, report narratives) call `llmJson` with a JSON-only prompt outside any transaction, validate the answer and fall back to a deterministic result; a report narrative is additionally checked figure by figure against the report's own numbers.

## 8. Configuration over hard-coding

`config_options` (typed option lists), `priority_matrix`, `custom_field_definitions`, `business_calendars`/`holidays`, `sla_policies`/`sla_targets`, `assignment_rules`, `escalation_rules`, `notification_templates`/`notification_rules`, `approval_workflows`, `catalog_items` (with JSON form schemas), `ci_types` (with attribute schemas), `ci_relationship_types`, `report_schedules`, `report_definitions` and `system_settings` are all data with administration screens. The seed provides a working NOC/SOC/AMC operating model on first start.

## 9. Repository layout

```
apps/api        Fastify API, workers, migrations, seeds   (see src/modules/* for each capability; software/ holds the catalogue, installations, licences, compliance, import and overview)
apps/web        React SPA (pages per module, shared UI kit)

```

**Navigation.** `packages/shared/src/appmap.ts` holds `APPLICATIONS` and `APP_PAGES`, the one list of applications and pages shared by the web navigator (`apps/web/src/layouts/nav.ts`, grouped into Insight, Service desk, Service operations, Accounts, Infrastructure and System, with the portal's Support, Your services and Account), the module strips (`apps/web/src/layouts/modules.ts`), the administration rail (`apps/web/src/components/admin/AdminLayout.tsx`), the assistant's guide and navigation tools, and the tests (`ai-appmap.test.ts`, `navigation.test.ts`). Adding a page means a route, an `APP_PAGES` entry, a navigator child under its application and a strip entry; the tests fail until all four agree.
