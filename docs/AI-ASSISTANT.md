# Grady, the assistant: architecture, skills, tools and guardrails

Grady is the chat assistant in the staff application and the customer portal. It knows every application and page of Progression, reaches every module through the platform's own services under the caller's permissions, and acts only through previews the person confirms. This page is the contract for how it works and how to extend it. The design follows what ServiceNow Now Assist and Virtual Agent, and SymphonyAI Apex, do: skills with structured playbooks, context awareness (who, where, which record), permission-scoped tools, grounded answers with record links, propose → preview → confirm → execute → audit with autonomy tiers, an administrator's control page and defence in depth.

## One turn

```
web panel ──POST /ai/chat (JSON or text/event-stream)──▶ chatTurn(principal, meta, input, emit)
WhatsApp  ──webhook ▶ whatsapp_inbound ▶ job whatsapp-chat ──▶ chatTurn(principal, meta, { channel: 'whatsapp' })
  A (tx)   guards (kill switch, feature switches, daily budget), the conversation, the user's message, the held action
  C (tx)   a confirm/cancel bound to the held action's id: SELECT … FOR UPDATE, run the tool exactly once, audit, reply "Done: …"
  B (tx)   history, screen and page context, toolset resolution
  loop     provider.chat({ stable, volatile }, tools) with NO transaction open; each tool call runs in its own
           short transaction under the caller's identity (source = 'ai'): validate → preview | run → scrub secrets →
           tenant fence → wrap people-written text as data → truncate → audit ai.tool
  ground   facts first when the reply does not state them; links (everyone) and ticket numbers (portal) fenced
  D (tx)   the reply, the conversation state (pending action, toolsets), audit ai.chat, UI actions
  render   WhatsApp only: the reply as WhatsApp text (bold, bullets, absolute links, the YES/NO footer), sendText, an outbox row assistant.reply
```

Model calls never hold a database connection (`apps/api/test/ai-transaction.test.ts` proves it). The streamed route emits `open`, `turn`, `toolsets`, `step` (tool start, done, error) and `message` events, or an `error` event, with keep-alive pings; the JSON reply is the default and what the tests use.

## The prompt (`apps/api/src/modules/ai/prompt/`)

Fixed sections in a fixed order, rendered as two blocks. The **stable** block depends only on the role and the permission profile, so the provider caches it across turns and people: identity and the application list (`identity.ts`; the list is `APPLICATIONS` in the application map, in the navigator's order and with the navigator's labels, so Grady names applications the way people see them), the rules in six groups (`rules.ts`: grounding, authorisation, confirmation tiers, privacy and tenant, untrusted content, refusals and limits), the house style with placeholder-only examples (`style.ts`), and the role's skill playbooks (`skills/`). The **volatile** block changes every turn: the operating context (`context.ts`: date and timezone, who, scope, autonomy, active skill, current page and record, turn notes such as a cancelled proposal) and the capabilities of the turn (`capabilities.ts`: enabled toolsets, tools by tier, the groups the model may enable). `PROMPT_VERSION` (`version.ts`) is bumped whenever the stable wording changes and is stored on every reply, so an answer can always be traced to the prompt that produced it. `apps/api/test/ai-catalog.test.ts` asserts the section order and that nothing date-, user- or tool-specific sits in the stable block.

## Skills and slash commands

A skill is a playbook: when it applies, the toolsets it works with and the steps to follow. Ten exist: lookup, triage, act, incident (major incidents and on-call: who is on call, paging through a policy), approvals, knowledge, analyse, navigate, admin and self-service. Staff get every playbook whose toolsets they have tools for; portal users get lookup, knowledge, analyse, navigate and self-service. A `skill` in the chat body forces its toolsets and names it in the operating context; the panel's slash commands do that: `/status`, `/triage`, `/new`, `/incident`, `/approve`, `/report`, `/find`, `/kb`, `/admin`, `/help`, each shown only when the person has the skill.

## Toolsets and routing (`toolsets.ts`)

Every model call carries the core and navigation tools plus at most four extra groups: tickets, triage, incident, approvals, customers, contracts, cmdb, assets, field, knowledge, reports, config, admin, iam. A group is enabled by the skill, the current page (the application map lists which groups fit each page), a deterministic keyword router over the message, the groups the conversation already used (stored on the conversation), or the model calling `enable_toolset`, in that priority. A group is offered only when the person has at least one of its tools. Definitions are emitted in registry order so an identical set serialises to identical bytes for the provider's cache.

## The tool catalogue (`tools/`)

159 tools (92 read including the two hidden ones, 67 actions) in one registry split by module. Each declares its toolset, tier, staff permissions (`requires`, all needed, plus optional `anyOf`), portal permissions (`portal`, or `null` when not offered to customer users; `portalOnly` for self-service actions), `run`, a one-line `summary`, a `preview` for actions (resolved against real records, with the exact change lines and the record count for bulk and destructive actions) and the query caches the web refreshes afterwards. Every tool wraps the service function the page uses, with the caller's `Ctx`, so row-level security and `ctx.require` apply exactly as in the UI. `query_tickets` remains the one semantic layer for ticket figures: exact totals with a plain-language definition and `facts` lines, the same predicates as the ticket list, no SQL from the model. `run_report` answers with the report's derived insights (trends against the previous period, targets, concentrations, best and worst) and next steps beside the figures, and `export_report` takes a format (csv by default, xlsx, html or pdf for the branded document); because tools run inside their own transaction, the files they store carry the rules' narrative.

Tiers decide when a tool may run: `read` freely; `write_low` (work notes, tasks, links, watching, time, bridge notes, article feedback, CSV exports, sticky notes) immediately only under autonomy `auto_low`; `write` after a confirmation; `outbound` (customer-visible stakeholder updates, scheduled report deliveries), `admin` (settings, option lists, rules, workflows, templates, SLA policy attributes) and `destructive` (cancel, delete, unlink, bulk) always after a confirmation, with the preview naming every record and count. People, roles, permissions and integration keys are read-only through the assistant by decision; protected settings (`security.*`, `smtp.*`, anything named like a secret) are never read or written.

## Propose, preview, confirm, execute, audit

An action tool never runs on the turn the model calls it. The platform resolves the preview, stores the action on the conversation with an id, a tier and an expiry (30 minutes), and the model asks "Shall I proceed?". The panel shows the card with Confirm and Cancel bound to that id; a typed yes or no still works and resolves to the single held action. The decision runs in a transaction that locks the conversation row, so two simultaneous confirmations run it once; a mismatched or expired id answers 409 `stale_action`. Every side effect of a confirmed action carries `aiActionId` and `aiConversationId` in its audit metadata. Each turn is audited as `ai.chat` (outcome, tools, tokens, cache reads, duration, model, prompt version, fences, toolsets, skill) and each tool call as `ai.tool` (tool, tier, outcome, an input fingerprint, never the input).

## Guardrails

- **Row-level security and the service layer**: nothing the person cannot open in the UI exists for the assistant.
- **Tenant fence and answer fence**: for customer users every tool result is scanned for records of another organisation (removed, logged, audited as `ai.tenant_fence`), and the reply may only link records and name ticket numbers that this conversation has shown (`ai.answer_fence`). Staff replies are link-fenced too.
- **Untrusted content**: descriptions, comments, articles, event payloads and other people-written fields are sanitised (control and invisible characters removed) and wrapped as `«data» … «/data»`; the rules declare that text as information, never instruction, and any marker the model echoes is stripped from the reply.
- **Secrets**: tool results, stored action inputs and traces are scrubbed of values under secret-looking keys; the prompt carries no credentials.
- **Limits**: 30 messages per minute per person on `/ai/chat` and the model-backed suggestion routes, a daily token budget per person, a wall-clock budget per reply, a cap on tool iterations and result sizes, provider timeouts and one retry.
- **Kill switches**: the assistant and each feature can be switched off by an administrator; the switch takes effect on the next message.
- **Retention**: conversations untouched for longer than `ai.conversation_retention_days` are deleted nightly (`conversation-purge` on the `ai` queue).

## Triage on arrival and the composer helpers

A moment after an incident or request is created, the `triage-ticket` job on the `ai` queue runs `triageTicket` (`apps/api/src/modules/ai/triage.ts`): the classification (keyword heuristic, refined by the model when a provider is configured), the owner recommendation (assignment rules, the service default, the CI owner team, recent resolvers and open load) and the duplicate check (same customer, similar title or shared configuration items, open tickets only), plus matching knowledge articles. Each result is stored as an `ai_suggestions` row flagged `triage`. At or above `ai.triage.auto_apply_confidence` (85 by default) the category and subcategory are applied to a ticket that arrived without one, and an owner is assigned to an unassigned ticket; priority is never changed without a person. Below the threshold the rows stay `proposed` and the ticket page shows them as **Grady triage** chips under the attention strip, each with Apply and Dismiss; Apply goes through `POST /ai/suggestions/:id/decide` with `apply: true`, which carries the change out through the ticket services under the person's own permissions and marks the row `applied`. Tickets raised by monitoring, the SIEM or the API that look like an open ticket are linked as `duplicate_of` the oldest one when `ai.triage.storm_auto_link` is on; `ai.triage.storm_threshold` look-alikes within `ai.triage.storm_window_minutes` is an alert storm and is said so in the activity. Every run writes one `Grady triage: …` activity (internal) and an `ai.triage` audit entry; a retried job is a no-op. The `triage` feature switch turns the whole thing off.

On the ticket page the reply composer offers **Draft reply** (a tone menu: neutral, formal, friendly, apologetic; the draft lands in the box with a provenance line) and **Suggest knowledge** (matching articles with an *Insert link* button); the resolve dialog offers **Write with Grady**, which drafts the customer-visible resolution notes from the work notes (`POST /ai/tickets/:id/draft-resolution`); the actions menu offers **Summarise for handover…**, the ticket summary with key facts and next steps ready to copy. All of it is staff-only, needs `ai:use`, and follows the feature switches (`draft`, `suggest_kb`, `summarize`).

## Changes

`change_calendar` (tickets toolset, read) returns the changes scheduled in a period with their window, type, status, risk, assignee and scheduling conflicts (shared systems, the same business service, blackout windows), plus the blackout windows in force, as `facts` lines the model quotes. The change impact analysis (`POST /ai/changes/:id/impact`) gathers the stored conflicts and the questionnaire's level and score; both raise the heuristic risk level and appear in the summary and the recommendations.

Six tools close the gaps (`tools/changes.ts`): `standard_changes` (tickets, read) lists the standard change catalog with each template's type, risk, category, service, downtime, pre-approval and usage ("which standard changes can I raise for ABC"); `raise_standard_change` (tickets, action, tier write, `tickets:create`) raises a change from a template for a customer with a window, site, configuration items and assignee, previewing the clashes and refusing a blackout window when the blocking setting is on; `cab_agenda` (approvals, read; `changes:cab`, `changes:approve` or `changes:manage`) returns the next meetings or one meeting by title with the agenda, the decisions, the minutes and the changes awaiting the board on no agenda; `add_to_cab_agenda` (approvals, action, tier write, `changes:cab`) tables a change on the next meeting or a named one with a note; `assess_change_risk` (tickets, action, tier write, `tickets:update`; a change manager on any change, otherwise the raiser or the assignee) scores a change from answers given as question wording and option wording, the preview showing the computed score, and with no answers lists the questions; `planned_changes` (tickets, read; `portal:status` in the portal) answers "what changes are planned for us" with the window, the customer-facing state, the downtime and the services touched, pinned to the customer's own organisation for portal users. The lookup, act, approvals and self-service playbooks name them; a CAB meeting page tells Grady which meeting is open. `changes.reminder_hours`, `changes.conflict_warnings`, `changes.block_blackout_scheduling`, `changes.require_assessment_for_approval` and `changes.portal_horizon_days` are settings Grady may change with confirmation (validated).

## Announcements

`POST /ai/announcements/draft` (`draftAnnouncement` in `apps/api/src/modules/status/draft.ts`) writes a title and a body for a type and an audience from a ticket (number, title, status, priority, customer, affected systems, description, latest stakeholder update, change window) or free notes, against `ANNOUNCEMENT_SYSTEM`, with a template per type when no provider answers. The Announcements page and the major incident command card call it; nothing is published until a person presses Publish. In chat, `create_announcement` (incident toolset, outbound tier, `announcements:manage`) previews the title, the body, the audience and the customer and publishes on confirmation; the incident playbook tells Grady to write for the audience and to let the user approve the wording.

## Shift handover drafts

`apps/api/src/modules/ai/digest.ts` builds the operations digest for one team (counts and short lists through the caller's context, so row-level security and the SOC fence apply) and `renderHandover` turns it into the deterministic note. `handover/service.ts draft` gathers the facts in one transaction, calls `llmJson` against `HANDOVER_SYSTEM` outside it (the Steps pattern) and falls back to the rendered note when the provider is off, the `handover` feature switch is off or the answer is unusable. The `shift_handover` read tool (toolset incident) returns the digest facts and the latest handover; the incident playbook tells Grady to answer "what should the night shift watch" from them and to send people to the Handover page to write or acknowledge one.

## Daily briefings

`modules/briefings/definitions.ts` holds one definition per role (engineer, NOC manager, SOC manager, service manager, account manager) that builds a structured fact sheet (headline sentences and sections with referenced items) through the person's own context; the operations managers' briefings reuse `buildDigest`. `briefings/service.ts generate` gathers in one transaction, calls `llmJson` against `BRIEFING_SYSTEM` outside it and falls back to `renderBriefing` (the same headings, the facts as bullets) when the provider is off, the `briefing` feature switch is off or the answer is unusable; `markdownToHtml` turns the result into the email. The scheduler (`jobs/processors/briefings.ts`) runs every fifteen minutes and generates under each person's own identity at their chosen local time. Generation on request is guarded by `ai.briefing.max_per_day` and `ai.briefing.cooldown_minutes` (`usageOf` in the service): once the cap is reached, or inside the cooldown, the stored briefing is returned with `reused: true` and the model is not called.

## Report insights and recommendations

Every report document carries insights and next steps, and the assistant only rephrases them. The rules live in `apps/api/src/modules/reports/insights.ts` (a trend against the previous period, a figure against its target, a category holding 40% or more of a chart, the weakest and strongest category of a percentage chart, a spike in a time series, a clean sheet when an exception list is empty) and the service review pack's recommendations in `definitions/service-review.ts` (breaches and the weakest priority, major incidents, reopen rate, first-contact resolution, backlog growth, after-hours arrivals, open known errors, change success, low ratings, exhausted or warning entitlements, expiring asset cover, licence positions, PM on time, out-of-scope work). `executeReport` runs the definition, its previous-period comparison and the rules inside one transaction, then, for HTML, PDF and Excel runs made through the route or the worker (the Steps pattern), calls `phraseNarrative` against `REPORT_NARRATIVE_SYSTEM` outside any transaction, and stores the run row and the file in a second transaction; the model receives the figures, the insights and the rules' own wording and returns the summary and the three lists, every sentence of which is kept only when each number in it appears in the input (`groundedAgainst`), an empty list falling back to the rules. The `recommendations` feature switch (*Report insights and recommendations* on the control page) and the `reports.narrative` setting both have to be on; JSON previews, CSV, Grady's `export_report` and tool runs never call the model and always carry the rules' wording, and the run's audit record says which source the document holds.

## Customer sentiment

`apps/api/src/modules/ai/sentiment.ts` labels every customer-written comment a moment after it lands (`comment-sentiment` on the `ai` queue, enqueued by `addComment`; `sentiment-sweep` every ten minutes catches anything missed and marks staff comments `n/a`). The model answers `{sentiment, score, reason}` against `SENTIMENT_SYSTEM`; without a provider, or when the answer is not valid JSON, `lexiconSentiment` decides from a word list, capitals and exclamation marks. The label goes on the comment and as `lastSentiment` on the ticket; a negative or angry comment adds an internal activity, an `ai.sentiment` audit entry and the `ticket.sentiment_negative` notification to the assignee and the team manager, at most once per ticket every six hours. Portal users never see the label; staff see it on the ticket list, in the rail, in the attention strip and through the `sentiment` predicate of `query_tickets`, which, with `breachRisk`, also lets Grady answer "which tickets are likely to breach" and "where is the customer unhappy" with exact figures. The `sentiment` feature switch turns it off.

## The application list and the navigator

Grady and the navigator read the same list: `APPLICATIONS` in `packages/shared/src/appmap.ts` is printed in the identity block of the stable prompt and returned by `app_guide`, and the web navigator shows its entries in that order with those labels (`apps/api/test/navigation.test.ts` keeps them in step). Changes (the change calendar, CAB meetings and risk scoring) is an application of its own in both places, so "where do I see the CAB" is answered with Changes, not Operations; the pages keep their routes, and the page keys of the calendar and the CAB moved under `changes.*`. Because the list is part of the stable block, this change moved `PROMPT_VERSION` to 2.5.0.

## Known errors

Five tools in `tools/known-errors.ts` (knowledge toolset) cover the known error database. `known_errors` (read; `kedb:read`, `portal:kedb` in the portal) searches the entries by words, customer, service, status and publication and returns the counts as facts (open, with a fix in progress, published) with the workaround of each entry; `get_known_error` (read) returns one entry by problem number with its symptoms, root cause, workaround, permanent fix, fix change, linked incidents, configuration items and portal wording; `match_known_errors` (read; also `tickets:read`, `portal:tickets` in the portal) takes a ticket and returns the linked known error or the best matches for the incident, so "is this a known issue" is answered from the database rather than from memory; `mark_known_error` (action, tier write, `problems:manage`) flags a problem with a status, a workaround, a root cause and a fix change, previewing the first lines of each; `publish_known_error` (action, tier outbound, `kedb:publish`) publishes the customer-facing summary and workaround to the organisation's portal and previews what customers will read and how many portal users are notified. Portal users get the published entries of their own organisation only, with the customer wording; every free-text field in a result is fenced as untrusted content, and a foreign ticket is refused. The knowledge playbook sends known-issue questions to these tools before any article search, the triage playbook asks for the best match and proposes `link_tickets` with `problem_of`, and the lookup and self-service playbooks name the read tools (`PROMPT_VERSION` 2.7.0). **Write with Grady** in the publish dialog calls `POST /ai/known-errors/:id/draft` (`draftCustomerWording` in `modules/known-errors/draft.ts`), which gathers the problem in one transaction, calls `llmJson` against `KNOWN_ERROR_SYSTEM` outside it and, when the provider is off or the answer is unusable, assembles the wording from the symptoms and the workaround with hostnames and addresses removed; the `kedb_draft` feature switch (*Drafted customer wording for known errors*) turns the route off (503) without touching anything else. `known_errors.notify_customers`, `known_errors.suggest_limit` and `known_errors.resolve_on_fix` are settings Grady may change with confirmation (validated).

## Customer satisfaction

Four tools in `tools/surveys.ts` cover the satisfaction surveys. `csat_summary` (read, reports toolset; `surveys:read`, `portal:access` in the portal) answers "what is our CSAT this month" and "how satisfied is this customer, by engineer" with the exact figures of a period (average rating, share satisfied, response rate, responses, surveys sent, low ratings), the rating distribution, the breakdown by customer, engineer, team, service, priority, channel or month and the lowest-rated tickets; `csat_low_ratings` (read, reports toolset) lists the tickets rated at or below a threshold with the comment, the respondent and the channel, for "which tickets got a poor rating at this customer"; `send_survey` (action, tier outbound, `surveys:manage`) sends or re-sends the survey for one ticket after a preview naming the recipient, bypassing sampling and fatigue; `rate_ticket` (action, tier write, portal only, `portal:tickets`) lets a customer rate one of their own tickets in the conversation ("rate INC-001234 four out of five, the engineer was quick"), previewed and confirmed, recorded with the channel *assistant*. Portal answers are pinned to the caller's organisation: a breakdown by customer, engineer or team is answered by service instead, engineer and team names are never returned, and a ticket of another organisation is refused. The reports toolset is enabled by the words survey, CSAT, satisfaction, rating and rated; the analyse playbook names the two read tools, the act playbook `send_survey` and the self-service playbook `rate_ticket` (`PROMPT_VERSION` 2.8.0). The `surveys.*` settings are among those Grady may change with confirmation (validated).

## Task boards

Three tools in `tools/boards.ts` (tickets toolset, staff only: `portal` is null on all three) cover the task boards. `my_board` (read, `tickets:read`) answers "what's on my board" and "am I over my WIP limit" with the person's ticket or task board as exact facts: the cards per lane, how many carry a breached SLA or fall due within four hours, whether the person is within or over the work-in-progress limit, the state of their team's latest shift handover (published and acknowledged by whom, published and not yet acknowledged, still a draft, or none written yet) and the number of sticky notes, with the cards themselves (number, title, lane, priority, customer, due, link) and a link to the board. `team_board` (read, `tickets:read`) does the same for a team or one engineer, by status or by assignee, and names who is over the WIP limit, so "how loaded is the NOC" and "who is over their limit" are answered from the lane figures the board shows, never from memory; the SOC fence and customer visibility apply as on the ticket list. `add_board_note` (action, tier write_low, `tickets:read`) adds a sticky note to the person's own board after a preview of the text, its colour and whether it is pinned, and the panel refreshes (`invalidates: ['boards']`). The tickets toolset is also enabled by the words board, kanban, lanes, swimlanes, sticky notes, my board and WIP; the lookup playbook has a Boards step, the act playbook names `add_board_note`, and the incident playbook ends by pointing at the board page (`PROMPT_VERSION` 2.9.0). No feature switch and no model call: the tools read the same service the page uses. The `boards.*` settings are among those Grady may change with confirmation (validated).

## Software and licences

Six tools in `tools/software.ts` (assets toolset) cover software asset management. The four read tools branch on who is asking: staff with `software:read` go through the software service; customer administrators with `portal:software` go through the portal projections, which pin the organisation and carry no cost, key, paperwork, owner or notes, so "what software do we run" answers for their own organisation only. `software_inventory` lists the titles in use (installations, customers, licensed seats) for one customer or every customer, optionally narrowed by a search or a publisher. `software_compliance` answers "which titles are over-deployed at a customer" with the live position per customer and title (installed against entitled, unused seats, the position, the next licence end date) and a one-line fact with the over-deployed, unlicensed and under-deployed counts. `licence_renewals` lists what ends or renews within a window, expired first. `get_licence` opens one licence by name or id with its term, seats, installed count, position and, for staff, the commercial fields; for a customer administrator a name that is not theirs is refused, never redirected. `record_licence` and `record_installation` (actions, tier write, `software:manage`, `invalidates: ['software']`) create a licence or an installation after a preview that names the resolved customer, title, contract, CI or asset. `open_record` accepts `kind: 'licence'` (the licence record for staff, the portal software page for customer administrators). The assets toolset is also enabled by the words software, licence, licensing, installation, seats, subscription, publisher, over-deployed and compliance position; the lookup, analyse and self-service playbooks name the tools (`PROMPT_VERSION` 2.10.0). No feature switch and no model call: the tools read the same service the pages use. The `software.*` settings are among those Grady may change with confirmation (validated).

## Custom reports

`dashboard_kpis` (read, reports toolset, every staff user; `portal:access` in the portal) answers "how are we doing", "how many open incidents do we have" and "what is our SLA compliance this month" with the headline figures of a dashboard for a period and an optional customer: the `view` is `overview` by default (the Overview's desk numbers, the person's own day and the NOC, SOC and AMC strips they may see, with `management` kept as an alias of the old home dashboard), or `noc`, `soc`, `amc` or `engineer` (my work); the answer links to the page the person would open (`/`, `/dashboards/noc`, `/dashboards/soc`, `/dashboards/amc`, `/dashboards/my-work`) with the period and the customer in the query, and portal users get their own customer overview. Two tools in `tools/reports.ts` (reports toolset, `reports:build`, never offered to customer users) serve the report builder. `report_catalog` answers "what can I report on" and "which fields exist for visits": the twelve entities with their permissions, date fields and, for one entity, every field with its type and whether it can be grouped or aggregated, plus the operators per type; the full listing carries field counts only, so either shape fits the tool-result cap. `build_report` (action, tier write, `invalidates: ['reports']`) turns a specification (entity, columns, filters, grouping with aggregates, sort, period field, customer, sharing) into a saved custom report: the preview compiles and validates the definition (an unknown role key is refused there, so a confirmed proposal cannot fail on it), names the shape, the filters with the records' names, the period and the sharing, and runs a twenty-row sample so the person sees real rows before confirming; the run saves through the same service as the page and links to `/reports/builder/<id>`. `list_reports` marks custom reports and carries their builder link; `run_report`, `export_report` and `schedule_report` accept a custom report by name or by its `custom:<id>` key, under the same visibility and entity-permission checks as the catalogue. The reports toolset is also enabled by the words custom report, report builder, "build me a report", "save this as a report" and "grouped by"; the analyse playbook tells Grady to read the catalogue before proposing a report and to prefer a built-in definition when one already answers the question (`PROMPT_VERSION` 2.11.0). Separately, the builder page's *Describe it* box calls `POST /reports/builder/suggest` (Steps pattern, rate-limited, `reports:build` or `reports:manage`): with `ai:use`, a provider and the **Report builder suggestions** switch (`report_builder`) on, `REPORT_SPEC_SYSTEM` asks the model for a JSON specification over the catalogue it is given, which is validated like any other spec; otherwise, or when the model's answer does not validate, a deterministic fallback picks the entity, the group field and the period from the words in the sentence and the answer says `ai: false`. The `reports.*` settings are among those Grady may change with confirmation (validated).

## Notification preferences

Two tools in `tools/notifications.ts` (the `profile` toolset, offered to staff and to portal users with `portal:access`) act for the signed-in person only; nobody's preferences can be read or changed on their behalf, and nothing here calls the model. `my_notification_preferences` (read) returns the person's matrix for their audience (customer users get the ten customer rows with the customer wording): per category whether email and WhatsApp are on, which channels the administrator locked, and the state of their mobile number (opt-in, verified or not, masked as `+91••••1004`), with facts such as "14 notification categories: email on for 12, WhatsApp on for 13", so "what do I get on WhatsApp" and "am I getting SLA emails" are answered from the stored preference. `set_notification_preference` (action, tier `write_low`, `invalidates: ['preferences']`) switches one category and channel on or off after a preview that names the row and says what stays as it is; it is refused, with the reason, for a row the person is not offered, a channel the administrator locked ("SLA warnings and breaches cannot be switched off"), WhatsApp without an opted-in number ("Turn on WhatsApp notifications on your profile first") and an email-only row. The `write_low` tier means a person on the `auto_low` autonomy gets their own preference applied without the card; everyone else confirms. The toolset is enabled by the words notification, WhatsApp, opt in, opt out, preference, unsubscribe, mute, "stop sending", "email me", "message me", "my number" and "verify my number", and by the profile page; the act and self-service playbooks name the two tools (`PROMPT_VERSION` 2.13.0). The administrator's side is the existing `upsert_config` with kind `notification-categories`, which resolves a row by its key ("lock email for approvals" is `record: 'approvals', fields: { emailLocked: true }`) and links to the Notification defaults page; keys, sort order and new rows are refused, as is a lock whose default is off.

## Grady on WhatsApp

The assistant has a second entry point. A message to the business number arrives at the WhatsApp webhook, is verified with the app secret, stored in `whatsapp_inbound` (deduplicated by Meta's message id) and handed to the `whatsapp-chat` job on the `ai` queue (`modules/whatsapp/`); the job identifies the person, applies the gates and runs the very same `chatTurn` as the web panel under that person's own principal, so every tool, permission, tenant fence, confirmation, limit and audit entry of the web applies unchanged. Identity is proof of ownership plus consent: `users.whatsapp_verified_at` (a one-time code sent to the phone, or shown on screen and typed from the phone to the business number; the notification module's flow) and the flag `preferences.whatsapp.assistant` the person switches on from the profile card, or from the phone with START (STOP switches it off). A six-digit text with an open typed code links the number first; an unverified number gets the unlinked reply once an hour; a verified number with the chat off gets a notice once an hour; then the switches (`whatsapp.assistant.enabled`, the `whatsapp_assistant` feature, the provider), the audiences, the burst limit, the daily cap and `ai:use` are checked, and only then does the model run. One turn per phone at a time and in order: a message claims its row (`claimed_at`), a newer message from the same phone waits while an older one is being answered, a claim a dead run left behind is taken over by the job's next run once it is older than the reply timeout, and a ten-minute sweep re-queues messages whose job never ran. The daily cap and the burst limit count every turn that ran the model, whether or not Meta accepted the reply.

The turn carries `channel: 'whatsapp'`: the `ui` toolset is neither active nor offered (there is nothing to navigate on a phone), the operating context gains a volatile channel block (plain text, short answers, at most five records, the links from tool results, no navigation tools, how to propose an action) and one stable sentence in the navigate playbook tells Grady never to call `navigate`, `open_record` or `prefill_form` off the web (`PROMPT_VERSION` 2.14.0). The reply is rendered as WhatsApp text (`modules/whatsapp/render.ts`): bold for the headline figure, bullets instead of tables, headings as bold lines, app-relative links made absolute only at this point so the link fence still applies, a held action rendered as its preview lines plus "Reply YES to go ahead or NO to drop it", any UI action a model still produced rendered as an "Open …: URL" line, and long replies split at paragraph, line and word boundaries into at most four parts. The person's yes or no on the next message resolves the held action through the same confirm path as the web, without a model call, because the conversation is carried: the WhatsApp thread is the person's own `ai_conversations` row keyed by `context.channel = 'whatsapp'` (and the organisation for a portal user), reused until it has been idle for `whatsapp.assistant.thread_idle_hours`, and it appears in the web panel's history with a WhatsApp badge. Replies are sent as free text from the job and recorded as `assistant.reply` outbox rows with the provider message id, so delivery states land on them; the greeting goes once before the first reply.

What tells a WhatsApp turn apart in the audit log: `ai.chat` and `ai.tool` rows with request id `whatsapp:<message id>` and user agent `whatsapp`, and one `whatsapp.chat` row per handled message on entity `whatsapp_inbound` with the outcome. The usage report counts WhatsApp replies beside web replies. `whatsapp_chat_status` (iam toolset, read, administrators only, never offered to portal users) answers "is WhatsApp chat working": the switch, the readiness checks, how many people linked a number and the inbound, replied and failed counts over the last hours, with a link to the WhatsApp page. The `whatsapp.assistant.*` settings are among those Grady may change with confirmation (validated); the display number and the secrets are not.

## The control page

**Administration → AI assistant** (`/admin/ai`, `admin:system` or `admin:config`; writing needs `admin:system`) holds the provider connection and its test, the kill switch, autonomy, reasoning effort, the nineteen feature switches, the daily token budget, the reply timeout, the retention period, the fixed rate limit, and the usage report for 7, 30 or 90 days: replies, people, tokens with the cache share, tool calls, feedback, average reply time, fenced and denied events, replies and tool calls per day, the outcome mix and a per-tool table. The API behind it is `GET/PUT /ai/admin/settings` and `GET /ai/admin/usage`.

## The web panel

The window stays mounted while minimised, so the thread, the draft and the proposal card survive; Cmd/Ctrl+J toggles it in both shells and Escape minimises it. While a reply is prepared the panel shows one line per tool from the stream. Navigation tools return `uiActions` the panel executes with the router (and a toast); the application map validates every destination against the person's permissions on both sides. Every message carries the page context (route, parameters and the filters the page understands) and, on record pages, the record. Thumbs on each reply are stored on the message and counted on the control page.

## Extending it

Add a read capability as a tool that returns `facts` for anything numeric; add a side effect as an action tool with a `preview` and the right tier; put it in the toolset of its module and, when a page should enable the group, in that page's `toolsets` in the application map (`packages/shared/src/appmap.ts`, which must list every web route: `ai-appmap.test.ts`). Add a skill as a playbook in `prompt/skills/` and its toolsets in `SKILL_TOOLSETS`. Never add a tool that overlaps an existing one: overlap is what makes figures drift. Bump `PROMPT_VERSION` when the stable wording changes.
