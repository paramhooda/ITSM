# Operations guide

## Deployment topology

Minimum (single host):

```
docker compose up -d        # postgres, redis, app (API+web), worker
```

Recommended for production (high availability):

| Component | Guidance |
| --- | --- |
| `app` | 2+ replicas behind a load balancer / reverse proxy terminating TLS (`APP_URL=https://...`, `COOKIE_SECURE=true`). The API is stateless; sessions live in PostgreSQL, rate-limit counters in memory per replica (acceptable) or Redis. |
| `worker` | 1–2 replicas. Jobs are idempotent and locked via Redis/BullMQ; SLA and scheduled jobs are safe to run with multiple workers. |
| PostgreSQL | Primary + streaming replica (or Patroni/pgBackRest for automated failover). Size: 4 vCPU / 16 GB RAM handles 1,000+ tickets/day comfortably; set `shared_buffers` to ~25% RAM. |
| Redis | Standalone with AOF persistence (as configured) or Sentinel. Loss of Redis data is non-fatal: schedulers re-register on worker start and the notification outbox is replayed from PostgreSQL. |
| Storage | `/data/storage` volume for attachments. Use a replicated filesystem or NFS/SAN for HA; S3-compatible object storage can be added through the `StorageDriver` interface. |

Environment variables are documented in `.env.example`. All services read the same set.

## First start and upgrades

1. The `app` container runs migrations (schema → platform SQL for RLS/partitions → grants) under an advisory lock, then seeds defaults and the initial administrator (`ADMIN_EMAIL`/`ADMIN_PASSWORD`, only if no users exist).
2. Upgrades: pull the new image, `docker compose up -d`. Migrations are forward-only and idempotent; replicas can be rolled one at a time.
3. Rollback: restore the database backup taken before the upgrade and start the previous image.

## Backup and disaster recovery

* **PostgreSQL**: nightly `pg_dump -Fc` plus continuous WAL archiving (pgBackRest/WAL-G) for point-in-time recovery. RPO ≤ 5 minutes with WAL shipping; RTO is the time to restore and start containers.
* **Attachments**: snapshot the `storage-data` volume on the same schedule; attachments are referenced by `storage_key` so a restore of both database and volume is consistent (a newer volume than database is harmless; the reverse leaves dangling references that the download endpoint reports as missing).
* **Redis**: no backup required.
* Test restores quarterly: restore into a staging stack and run `GET /api/health` plus a login.

## WhatsApp notifications

WhatsApp is configured once under **Administration → WhatsApp** (Meta WhatsApp Cloud API): phone number id, a permanent system-user access token, the app secret (so delivery callbacks can be verified), a webhook verify token and the approved message templates. Business-initiated messages must use templates Meta has approved, so create one (the default is `progression_update` with three body parameters: subject, text, link) and map it on that page. The parameter list of a mapping must match the `{{1}}…{{n}}` placeholders of the approved template exactly: Meta rejects a mismatch with error 132000 ("number of localizable_params does not match"), which the test button reports with what to change; leave the list empty for a template without placeholders such as Meta's sample `hello_world`, in which case the test still sends it once without parameters and warns that notifications would carry no text; event groups (ticket, sla, incident, page, handover, briefing, and `user` for the verification code, which may be mapped to an authentication-category template) can map to their own templates and otherwise fall back to the default. The page sends a test message and lists recent WhatsApp rows of the outbox with their delivery state.

Three things must all be true before a notification reaches a phone, and the test message checks only the first: (1) the connection works (phone number id, token, an approved template mapped at least as the default); (2) the **notification rule** for the event lists the WhatsApp channel under Administration → Notification rules (the rule decides the channels of an event, the opt-in only decides who; new installations seed WhatsApp on every ticket, SLA, approval, field-visit and maintenance rule, and the WhatsApp page shows a warning with an "Add WhatsApp to these rules" button on databases whose rules predate the channel); (3) the person opted in with a mobile number, on their profile for staff, under Portal → Users or their own profile for customers, and has not switched the category off on their profile (Profile → Notifications; see Notification preferences below); verifying the number with the code is needed for chatting with Grady on WhatsApp, not for notifications. The events that reach a requester are a new ticket, a status change, an engineer's reply, resolution, closure and the satisfaction survey; editing a ticket's fields (title, description, priority, category) notifies nobody by any channel. Every message is queued in the outbox and sent by the worker within a minute, so when email arrives and WhatsApp does not, open Administration → Notification outbox filtered on WhatsApp: no row means the rule or the opt-in is missing, a failed row carries Meta's reason.

Everyone else opts in on their profile with a mobile number (ten-digit numbers get the default country code, India by default); customer administrators can do it for their users, and staff can tick it on customer contacts. A notification rule reaches WhatsApp only when the rule includes the WhatsApp channel and the recipient has opted in. Rows are written to `notification_outbox` with channel `whatsapp` inside the business transaction, delivered by the `deliver-outbox` job with retries, and marked failed at once on permanent provider errors (unknown template, invalid number). Register `/api/webhooks/whatsapp` in the Meta app (field `messages`) so sent, delivered, read and failed states flow back. The admin page shows the URL to register, derived from `APP_URL`; when the platform runs on localhost (Meta cannot reach it) enter the public URL of a tunnel such as ngrok in the **Webhook URL** field instead (`whatsapp.webhook_url`; an origin alone gets the webhook path appended, **Use default** goes back to the platform URL, and the page lists a local URL under "Still needed"). The override only changes what the page shows and copies: Meta calls whatever URL is subscribed there, and links inside messages still come from `APP_URL`. `WHATSAPP_API_BASE` overrides the Graph host for tests.

**Accepted but nothing arrives.** A message id from Meta only means the request was accepted; whether it reached the phone comes back through the status webhook (sent, delivered, read, or failed with a reason). The test message is recorded in the outbox like any other, so the page follows its state for two minutes after sending and shows the failure reason when one arrives (common codes are explained inline: 131026 no WhatsApp account or blocked, 131047 outside the 24-hour window, 131049 held back by frequency or quality limits, 130472 number in a Meta experiment, 132015/132016 template paused or disabled, 133010 number not registered). **Check connection** on the same page asks Meta about the phone number (registered and CONNECTED, display name approved, quality rating, messaging tier), every mapped template (exists in that language, APPROVED, placeholder count equals the mapped parameters, category) and whether an app is subscribed to the business account's webhooks, and lists what to change. When the check is green and no state ever arrives, the webhook URL set in Meta is not this platform's (or is local), the recipient's number has no WhatsApp account, the business is blocked by the recipient, or Meta is withholding a MARKETING template; use a UTILITY template for operational messages. Sent and failed outbox rows are purged after `notifications.outbox_retention_days` (90 by default) by the nightly `outbox-purge` job.

## Grady on WhatsApp

The same assistant that answers in the web panel answers on WhatsApp: a person who proved they own their mobile number and switched the chat on messages the business number and gets Grady with their own permissions, tenant fences, propose-then-confirm flow and audit trail, rendered as WhatsApp text. Nothing is duplicated: every message runs the same assistant turn under the person's own identity in the worker (`ai` queue, job `whatsapp-chat`), with no database transaction open while the model works.

Four switches must all be on before anyone gets a reply, and the readiness list on **Administration → WhatsApp** (card *Assistant on WhatsApp*) shows each of them: (1) WhatsApp enabled and configured (phone number id, access token); (2) the **app secret**, which is mandatory here: Meta signs every webhook delivery with it, and without it the platform cannot tell a real message from a forged one, so inbound messages are ignored (delivery states are still applied); (3) *Answer messages with Grady* (`whatsapp.assistant.enabled`, off on a fresh installation so a worker never answers a phone by accident); (4) the *Chat on WhatsApp* feature switch under Administration → AI assistant together with a configured AI provider. Switching WhatsApp off (the first switch) stops every send, the assistant's notices and confirmations included, exactly as it stops notifications. The card also holds who may chat (staff, customers, or both), the daily message cap per person (100 by default, on top of the AI token budget), the idle time after which a fresh conversation starts (24 hours), the greeting sent once before the first reply, the reply an unknown number receives, and the **display number** (the business number as people should message it, shown on the profile card and used for the wa.me link). Grady may change the `whatsapp.assistant.*` settings with confirmation; the display number and the secrets stay manual.

What Meta needs. In the app's WhatsApp configuration subscribe the webhook URL shown on the page (a public URL, or a tunnel on a laptop) with the verify token, and tick the **messages** field: delivery states and inbound messages arrive through the same `POST /api/webhooks/whatsapp`, each delivery signed with the app secret (`X-Hub-Signature-256`). The business number must be registered and connected (**Check connection** says so). Replies are free text, which Meta allows only within 24 hours of the person's last message; a reply is always an answer to a message that just arrived, so it is inside the window by construction. A message that waited longer than a day (the worker was down) is recorded as ignored and never answered, and a reply Meta refuses with error 131047 is recorded as failed and not retried. Every reply is an outbox row with event `assistant.reply` on the WhatsApp channel, so the outbox page and its delivery states (sent, delivered, read, failed) cover it; Meta retries deliveries it did not get an answer to, and a redelivered message is recognised by its id and handled once. Messages from one phone are answered one at a time and in order: a newer message waits while an older one is being answered. A turn the worker was restarted in the middle of is taken over by the next run of its job once its claim is older than the reply timeout, and the `whatsapp-inbound-sweep` job (every ten minutes) asks again for any message whose job never started and records a claim older than an hour as failed, so no message sits unanswered without a trace.

How people link a number. On **Profile & preferences** the card *WhatsApp chat with Grady* offers two ways to prove the number: a six-digit code sent to the phone (the same code flow as under Notifications; it needs a template mapped at least as the default) or a code shown on screen that the person sends from the phone to the display number ("I'll send the code"; the card links the number the moment the message arrives). Codes expire after ten minutes, three may be requested an hour, five wrong tries void one, and a code is bound to the account and the number, so a code sent from another phone links nothing. Verification never turns on notifications; the card offers the opt-in separately. With a verified number the person switches the chat on (*Turn on chat*) and off again (*Turn off chat*, or by texting STOP; START turns it back on); the number stays verified either way. Changing the number on the profile clears the verification. Administrators revoke a number from Administration → Users (*Revoke number*: chat off and verification cleared), customer administrators from Portal → Users for their own organisation; nobody can switch the chat on for somebody else.

What a number gets. An unknown or unverified number receives the unlinked reply at most once an hour; a verified number with the chat off receives a short notice once an hour; a number excluded by the audiences, an account without the assistant permission, an unsupported message (image, voice note, location: text only, no transcription) and the daily cap each get one notice an hour; more than thirty messages a minute from one person are dropped silently; reactions are recorded and ignored. A proposed change ends with "Reply YES to go ahead or NO to drop it" and the person's yes or no decides it exactly as the typed yes or no in the web panel does, within the same thirty minutes. Portal users are fenced exactly as in the portal: their own organisation, their own conversation, customer wording, no internal data.

When nobody gets a reply: the readiness list first; then *Recent inbound messages* on the same page, which shows every message (number masked) with its outcome (replied, linked, chat on or off by START or STOP, unverified, chat off, switched off, not allowed, unsupported, throttled, daily cap, inactive account, failed, ignored) and the state of the reply; then Administration → Notification outbox filtered on WhatsApp; and the worker log line `whatsapp chat handled` with the outcome. The usage report under Administration → AI assistant counts WhatsApp replies, and Grady's `whatsapp_chat_status` tool answers "is WhatsApp chat working" for administrators. Inbound rows are purged with the outbox after `notifications.outbox_retention_days`; every handled message is one `whatsapp.chat` audit entry, and the assistant's own `ai.chat` entries carry `whatsapp` as the user agent. `WHATSAPP_API_BASE` points the client at a stand-in for the Graph host in tests.

## Major incidents

An incident becomes a major incident from its actions menu (**Declare major incident…**, permission `tickets:major`, incidents only) or by ticking the flag while raising it. Declaring writes a `major_incidents` row next to the ticket: bridge link and notes, incident commander (defaults to the assignee), communications lead, update cadence (30 minutes by default) and whether the customer portal shows a banner. The response team hears about it through the `incident.major_declared` rule (assignee, team, manager, account manager and the NOC, SOC and service managers over email, in-app and WhatsApp).

The **Major incident** tab on the ticket is the command view: stakeholder updates go to a chosen audience (requester, customer contacts, watchers, account manager, assignee, team, manager) over chosen channels and land in the communication log with how many people they reached; bridge notes join the log without notifying anyone; Grady drafts either kind from the record and the latest notes (`POST /api/ai/tickets/:id/major/draft-update`). Other incidents for the same outage are linked as children (`child_of` links, visible from both ends). Every stakeholder update resets the cadence; the `major-update-reminder` job (every 5 minutes) reminds the communications lead, or the commander, or the assignee, once per missed slot through `incident.major_update_due`. Resolving or closing the ticket resolves the major record, stops the cadence and sends `incident.major_resolved` to the requester, contacts, watchers and account manager; reopening re-activates it. After resolution the same tab holds the post-incident review (what happened, impact, root cause, owned actions); completing it closes the record. **Not a major incident…** demotes: the flag and the banner drop, the record stays for the audit trail.

**Operations → Major incidents** lists every major incident the viewer can see (active first, overdue updates flagged) and the NOC dashboard shows the active ones with their bridge. Customers see active incidents with the banner switched on above every portal page (`GET /api/portal/banners`) together with the latest stakeholder update, and the ticket itself carries the badge.

## On-call and paging

**Operations → On-call** (`oncall:read`; editing needs `oncall:manage`) is where a team's cover is defined and read. A **rota** belongs to a team and lists people in rotation order: the first starts on the start date at the handoff time (`09:00` by default) and the rota hands over every week, every day or every N days, in the rota's own timezone, so a handoff stays at 09:00 local across a daylight-saving change. A rota may cover a daily window only (for example `18:00`–`08:00`); outside it nobody from that rota is on call. A team can have several rotas (primary, secondary); the lowest order is paged first. **Cover** (an override) puts a named person on a rota between two instants whatever the rotation says; managers add cover for anyone, everyone else only for themselves, from the calendar. The Schedule tab shows who is on call now for every team with a rota (name, phone, email, until when, cover marked), the week calendar for one team and the cover entries; `GET /api/oncall/now` and `GET /api/oncall/schedule?teamId&from&to` (62 days at most) serve the same data, and the NOC and SOC dashboards carry an **On call now** panel.

An **escalation policy** is an ordered list of steps: whom to reach (whoever is on call for the team, a named person, every member, or the team manager), over which channels (email, in-app, WhatsApp) and how many minutes to wait before the next step; the whole list can repeat, and a policy can hand an unassigned ticket to whoever acknowledges. Each team has a default policy (Administration → Teams, or the Rotas tab of the on-call page). A **page** starts from a ticket's actions menu (**Page on-call…**, `tickets:escalate`), from an escalation rule (Administration → Escalation rules: *Notify on-call engineer* adds the on-call person to the notification; *Page on-call through* starts a page through the team's policy or a named one), or from Grady (`page_on_call`, confirmed first). The first step's people get `page.sent` with a one-tap acknowledgement link (`/api/oncall/ack/<token>`; the WhatsApp message carries that link, the email a button); the link shows a confirmation page on GET, since messaging apps prefetch links, and acknowledges on POST. When the step's timeout passes without an acknowledgement the step is marked escalated and the next one starts; when the last step times out the page expires and the team manager plus the NOC, SOC and service managers get `page.expired`. Acknowledging from the link or from the ticket's **Paging** tab closes the chain, records who took it, assigns the ticket when the policy says so and tells whoever paged (`page.acknowledged`). Resolving, closing or cancelling the ticket calls a waiting page off. Every step is an activity on the ticket and an audit entry (`ticket.page`, `ticket.page_ack`, `ticket.page_expired`, `ticket.page_cancel`); `GET /api/oncall/pages` lists them.

Timeouts are enforced twice: `page-timeout` on the `paging` queue is enqueued with a delay when a step starts, and `page-sweep` (every minute) moves on any waiting step whose deadline passed, so a lost Redis never loses a page. Tokens are stored hashed; the acknowledgement endpoints are rate limited per IP and reveal only the ticket number and title.

## Monitoring

* `GET /api/health` → `{status, db, latencyMs}`; the Docker healthcheck uses it.
* Logs are JSON on stdout (`LOG_LEVEL`), with `reqId`, route, latency and errors; ship them with your existing log pipeline.
* Suggested alerts: health check failing; `notification_outbox` rows in `failed` status; `ticket_slas` rows breached but not yet notified (`warned_at`/`breached_at` null past due); worker not running (BullMQ schedulers stop advancing); PostgreSQL replication lag; disk usage on the attachments volume.
* Administration → System shows outbox status and audit activity.

## Data growth

| Table | Strategy |
| --- | --- |
| `audit_log`, `integration_events` | Monthly range partitions created 3 months ahead by the maintenance job; dropped after `audit.retention_months` / `events.retention_months`. |
| `tickets`, `ticket_comments`, `ticket_activities`, `ticket_slas` | Indexed on `(customer_id, created_at)`, status, assignee, team, search vector. Millions of rows perform well. To partition tickets by month later: create `tickets_p` partitioned by `created_at`, copy, swap names in a maintenance window; application code does not change. |
| `metric_rollups_daily` | Nightly per-customer aggregates for dashboards and reports so they never scan history. |
| Attachments | Stored outside the database; metadata only in PostgreSQL. |

Routine maintenance: autovacuum is sufficient; run `REINDEX` on GIN indexes yearly if bloat is observed.

## Security operations

See `SECURITY.md`. Rotate `JWT_SECRET` to invalidate all access tokens (users re-authenticate via refresh cookie, which stays valid), rotate API keys from Administration → API keys, and review Administration → Audit log for privileged actions.

## Capacity planning (reference)

1,000 customers · 1,000 tickets/day · 10 comments/ticket · 3 SLA rows/ticket ≈ 5 M tickets, 50 M comments, 15 M SLA rows over 5 years, ~80 GB including indexes. A single PostgreSQL primary with 8 vCPU / 32 GB RAM and NVMe storage is adequate; scale reads with a replica if reporting load grows.

## Triage on arrival

Every new incident or request is triaged by Grady a moment after it is created (`triage-ticket` on the `ai` queue; the worker must be running). The job classifies the ticket, recommends an owner and looks for duplicates; above `ai.triage.auto_apply_confidence` the category and the owner are applied, otherwise they wait as proposals the engineer accepts from the chips under the ticket's attention strip. Monitoring and SIEM tickets that look like an open one are linked as duplicates of the oldest (`ai.triage.storm_auto_link`); `ai.triage.storm_threshold` look-alikes within `ai.triage.storm_window_minutes` is reported as an alert storm. The switch and the thresholds live on **Administration → AI assistant** (feature *Triage on arrival*, the Limits card); each run is a `Grady triage: …` activity on the ticket and an `ai.triage` audit entry. Without an AI provider the keyword heuristic still runs.

## Change management

**Calendar and conflicts.** Operations → Change calendar shows every scheduled change on a week or month grid (`GET /changes/calendar`). When a change is created with a window, its window or type is edited, or its configuration items change, `recordConflicts` (`apps/api/src/modules/changes/service.ts`) looks for another change of the same customer overlapping the window on a shared configuration item or on the same business service (through the dependency map), and for an active blackout window (global or the customer's; emergency changes pass when the window allows them). Conflicts are recorded once as an internal `change_conflict` activity and a `change.conflict` audit entry, never a block; the change plan tab, the calendar chips and Grady's change impact show them. `POST /changes/conflicts` previews the clashes of a window before the change exists. The setting `changes.conflict_warnings` turns the activity off.

**Blackout windows** (Administration → Blackout windows, `admin:config`): a name, an optional customer (empty = everyone), the window, the reason shown on the warning and whether emergency changes may go ahead. `changes.block_blackout_scheduling` (off by default) turns the warning into a refusal: a normal or standard change cannot be scheduled inside a blackout window (emergency changes pass when the window allows them); the record, the form and Grady show the clashes and the blackout as attention flags. On the change record the attention strip names the blackout ("Scheduled inside the blackout window …"), the clashes ("Clashes with 2 other changes"), a window that has no risk score yet and the CAB meeting the change is on; the plan tab previews the clashes while the window or the type is being edited, before Save. The ticket list's Changes tab carries three change pills — **Change type**, **Risk level** (including "Not assessed") and **Window** (the scheduled start between two dates) — which are cleared when another tab is chosen, and `GET /tickets` takes `changeType`, `riskLevel`, `scheduledFrom` and `scheduledTo`.

**Risk questionnaire** (Administration → Change risk questions): weighted questions with scored answers. On a change's plan tab the implementer answers them and presses Assess risk (`POST /changes/:id/assess-risk`): the weighted total is scaled to 0–100 against the questionnaire's maximum and mapped to low, medium or high with `changes.risk_thresholds` (`{ "medium": 35, "high": 65 }`); the level also sets the change's Risk field and is recorded as an activity and a `change.risk_assessed` audit entry. A high-risk change that is not yet approved is flagged in the attention strip. The questionnaire may be answered by anyone holding `changes:manage`, and by the person who raised the change or is assigned to it when they hold `tickets:update` (the questionnaire is the raiser's job). Thresholds are edited on the same page (`admin:config`, `PUT /changes/risk-thresholds`) and the question order is saved in one call (`POST /changes/risk-questions/reorder`); `changes.require_assessment_for_approval` (off by default) refuses an approval request or a CAB agenda slot until the change is scored; a fresh installation ships six questions and four standard templates.

**Standard change templates** (Administration → Standard change templates): repeatable changes with their plans; on the new-change form the template prefills the type, risk, category, service and plans (the API applies everything except the title, which the form takes from the template's default title); engineers browse them under **Changes → Change catalog** (`tickets:read`) as cards with the plans, the risk, the expected downtime and how often each was used, and raise one with **Raise this change** (`tickets:create`), which opens the new-change form prefilled. A pre-approved template sets the ticket's approval status to `not_required` (shown as Pre-approved) so no workflow is needed. Templates may be limited to named customers; the admin table shows how often each was used and when last, and the form takes a service. The API takes `changeTemplateId` on `POST /tickets`; `GET /changes/templates` filters by customer, category, service, type, pre-approval and a search, and returns the usage figures.

**CAB meetings** (Changes → CAB, permission `changes:cab`; `changes:approve` and `changes:manage` may read): a meeting has a chair, a time, a location or bridge link, attendees and an agenda of changes in the board's order. The **Awaiting CAB** tile lists the changes with a pending CAB step (or a pending approval) that are on no open agenda (`GET /cab/queue`), each with an Add into the chosen meeting; the Add change dialog on a meeting shows the same queue first and takes a note for the board, and every agenda row can be moved up or down and its note edited. Putting a change on an agenda notifies the requester and the assignee (`change.cab_scheduled`), and the change record shows the meeting in its attention strip and on the plan tab (with an **Add to a CAB meeting…** button when it is on none). Approving or rejecting an item records the decision on the change (`cab` activity; the CAB notes are appended, never overwritten) and, when a step is pending, decides the change's pending approval step (the CAB step first) through the approvals module; a rejection with no pending step moves an open change to Rejected with the usual status notification; deferring records only the decision. A meeting can be edited (title, time, chair, location, attendees) and cancelled, which clears the CAB slot on its changes, defers whatever was still undecided (so the CAB report never counts it as awaiting a decision) and writes a note on each. The location is shown on the meeting page and in the generated minutes only; the agenda notification never carries it, because the requester may be a customer contact. Closing a meeting marks what was not reached as deferred and keeps the minutes; when none were typed the minutes are generated (attendees, each decision with its notes, the deferred list) so a closed meeting always has a record. Meetings appear on the change calendar as a gavel pill on their day. The requester and the assignee are notified of decisions (`change.cab_decision`). The **CAB decisions** report (Reports, category Tickets) lists every decision by meeting with the deferred and pending items; the **Change calendar** report now carries the risk level and score, the template and the CAB decision.

**Portal.** Customers see their planned changes under **Service status → Planned changes** (`portal:status`, `GET /portal/changes`) for the next `changes.portal_horizon_days` (60) days and the last 30, with the window, a customer-facing state (planned, approved, in progress, implemented, cancelled), the expected downtime and the services touched, and the window on their change tickets; plans, risk, CAB and conflicts never reach the portal.

**Window reminder.** `change-window-reminder` runs hourly on the `sla` queue: open changes whose window opens within `changes.reminder_hours` (24) are reminded once (`change.window_reminder`, assignee, requester and team; `change_details.window_reminder_at` prevents repeats).

Grady: `change_calendar` answers "what is scheduled this week" with the windows, conflicts and blackout windows; `standard_changes` lists the catalog and `raise_standard_change` raises from it (with confirmation); `cab_agenda` reads the next meetings, their decisions and the queue, `add_to_cab_agenda` tables a change; `assess_change_risk` scores a change from the answers given; `planned_changes` answers "what changes are planned for us" (customers see their own organisation only); the change impact analysis includes the conflicts and the questionnaire's verdict.

## Shift handover

Operations teams (NOC, SOC, service desk) hand a shift over on **Operations → Shift handover** (`handover:write`; people with `oncall:manage` see and may write for every team). A team's shifts (name, start and end time of day, weekdays, timezone; an end at or before the start crosses midnight) are edited under **Administration → Teams → Shifts**; the seed gives the NOC and SOC a Day (08:00–20:00) and a Night shift and the service desk three, all in Asia/Kolkata. The page shows the shift running now and the next one, the live digest for the team (open tickets, P1/P2, breached and at-risk SLAs, unassigned, waiting on the customer, active major incidents, changes in the next 12 hours, who is on call now and at the next shift start, tickets opened and resolved since the shift began) and the lists behind each count. "Draft with Grady" writes the note from that digest and the engineer's own notes under fixed headings (Watch first, Open and at risk, Major incidents, Scheduled next, On call, Notes); without a provider, or with the `handover` feature switch off, the same headings are filled deterministically. The model is called outside the database transaction. Publishing stores the note with the facts it was written from and sends `handover.published` (email, in-app and WhatsApp for people who opted in) to whoever is on call when the next shift starts, or to every active member of the team when nobody is on a rota, never to the author. The incoming engineer opens it from the notification link and acknowledges it (with an optional note); the author cannot acknowledge their own handover. Drafts belong to their author; published handovers are kept and only an on-call manager deletes one. Everything is audited (`shift_handover` create, update, publish, acknowledge, delete; `team_shift` changes). Customer users and API keys never reach these tables (row-level security on `team_shifts` and `shift_handovers` admits staff only). Grady's `shift_handover` tool answers "what should the night shift watch" from the same digest.

## Daily briefing

Staff opt in on **Profile → Daily briefing**: a time of day in their own timezone, the briefing they want (automatic from their roles, or a chosen one they are allowed) and the channels (email, in-app). Every fifteen minutes the `briefing-scheduler` job on the `ai` queue finds the people whose local time has passed the chosen time and who have no briefing for their local day, and queues `generate-briefing` per person (idempotent id per person and day). The job runs under that person's own identity, so row-level security, the SOC fence and the customer scope apply exactly as on their dashboard. Five briefings exist, each built from exact figures: **engineer** (what is due next, breached or likely to breach, unassigned in their team, customers who sounded unhappy), **NOC manager** and **SOC manager** (per team: open, P1/P2, breached, at risk, unassigned, the watch list; major incidents; who is on call; integrations that sent nothing for 24 hours), **service manager** (SLA compliance by priority over seven days, escalated tickets, tickets likely to breach, major incidents, unhappy customers) and **account manager** (their customers' open and breached tickets, P1/P2 in progress, contracts ending within 60 days, entitlements running out, out-of-scope work this week). The model phrases the briefing when a provider is configured and the `briefing` feature switch is on (called outside the transaction); otherwise the same facts are rendered under the same headings. The dashboard shows a one-line card that opens the day's briefing in a dialog; "Brief me now" generates one on request (no delivery) and the email (`briefing.daily`) carries the same text with absolute links. Generating on request is capped so nobody can burn tokens by clicking: `ai.briefing.max_per_day` (default 3; 0 = unlimited) counts generations per person per day, and inside `ai.briefing.cooldown_minutes` (default 15) a request returns the stored briefing without calling the model; the dialog's Refresh button is off while either applies and says when it comes back. The scheduled morning delivery counts against neither. The route is also rate limited (10 requests per minute per person). Rows live in `briefings` (one per person and day, readable by that person only); `ai_disabled_features` can switch the feature off and a person turns it off on their profile. The Notifications card on the same profile lists the briefing as a row whose Email cell is the same choice as the card's Email checkbox (WhatsApp is not offered for briefings), and the administrator's Notification defaults page shows the row without toggles: the channels of the briefing belong to the person.

## Status page and announcements

**Announcements** (Operations → Announcements, permission `announcements:manage`) are banners shown above every page to their audience: everyone, customers only or staff only, optionally for one or more customer organisations, inside a window (show from, take down at), pinned or dismissible. Types: notice, planned maintenance, service disruption. Customers see them above every portal page and on their status page; staff see them under the shell header. "Draft with Grady" writes the title and the message from a ticket or from the text typed so far (a template without an AI provider); a major incident's command card offers **Draft announcement** pre-aimed at that customer. Grady can also propose `create_announcement` in chat (outbound tier, confirmed as written). The rows are shared (no customer column): `platform.sql` carries a hand-written policy (`app_is_msp()` plus the audience and customer list) so a customer scope only ever reads what is aimed at it; writes are staff-only. Audit actions `announcement.create|update|delete`.

**Service health and the status page.** `status-health` runs every two minutes on the `sla` queue (`apps/api/src/modules/status/health.ts`): for every business service (a CI of type `business_service`) it walks the dependency map and rates the service `down` (an active major incident on anything it relies on), `maintenance` (a PM visit in progress, a change inside its window or a dependency marked in maintenance), `degraded` (an open P1/P2 ticket or critical/high monitoring alerts in the last two hours on a dependency) or `good`, with the reasons, into `service_health_snapshots`. The portal's **Service status** page (`portal:status`, `GET /portal/status`) shows the customer's services with those reasons, planned maintenance for the next 14 days (PM occurrences and change windows), the announcements aimed at them and the major incidents being announced. Staff with `tenant:all` preview a customer's page with `?customerId=`.

**Public status pages.** On the Status pages tab (permission `customers:manage`) a link per customer is minted: the token is shown once, stored hashed, and listed by its prefix; revoke it to close the page. `GET /public/status/:token` (rate-limited, no sign-in) and `/status/:token` in the web return aggregate words only: service names and health, reasons in plain language, maintenance titles and windows, announcements, incident notices with the latest stakeholder update, never ids, ticket links or customer lists. Audit actions `status_token.create|revoke|delete`.

## Breach risk and customer sentiment

Two signals the queue reads at a glance, both staff-only (never in the portal, the customer dashboard or a customer's API responses).

**Breach risk.** `risk-score` runs every five minutes on the `sla` queue (`apps/api/src/modules/sla/risk.ts`). For every open ticket with an open SLA clock it takes the worst clock (percent of the target used, working minutes left), the median time to resolution of tickets of the same type, category and priority resolved in the last 180 days (the priority alone when the category has fewer than three samples), and the state of the ticket: no owner adds to the score, a paused clock caps it, waiting on the customer takes from it, an escalation or an earlier reopen adds a little. The result is `low`, `medium` or `high` with a 0 to 100 score and a one-line reason, written on the ticket (`breach_risk`, `breach_risk_score`, `breach_risk_reason`, `breach_risk_at`) only when it moved, and cleared when the clocks are done. The first rise to high adds an internal `Breach risk high: …` activity without touching the ticket's last-activity time. It shows as the **Risk** column and filter on the ticket list, the **Likely to breach** tile on the list and the NOC dashboard (linking to `/tickets?breachRisk=high`), the **Outlook** card in the ticket rail, the attention strip (when no clock is already breached or at risk) and the `breachRisk` predicate of Grady's `query_tickets`.

**Customer sentiment.** After every customer-written comment the `comment-sentiment` job on the `ai` queue labels it `positive`, `neutral`, `negative` or `angry` with a score from −100 to 100 (the model when a provider is configured, a word list with capitals and exclamation marks otherwise), on the comment (`ticket_comments.sentiment`) and as the ticket's last mood (`last_sentiment`, `last_sentiment_at`). A negative or angry comment adds an internal activity, an `ai.sentiment` audit entry and notifies the assignee and the team manager (`ticket.sentiment_negative`, in-app and email, with the usual notification rules on top) at most once per ticket every six hours. `sentiment-sweep` every ten minutes labels anything a lost job missed and marks staff comments `n/a`. The feature switch is *Customer sentiment on comments* on **Administration → AI assistant**. The mood shows beside the risk on the list, in the rail, in the attention strip (with a Reply action) and through the `sentiment` predicate of `query_tickets` (`unhappy` = negative or angry).

## Reports

Every report runs on screen (JSON preview) or as a stored file attached to a run: CSV, Excel, printable HTML and PDF. The HTML and PDF outputs are one and the same document, rendered server-side (`apps/api/src/modules/reports/theme/`): a light theme of its own, the Progression wordmark and typeface embedded as data, server-drawn SVG charts and no browser script, so the file opens the same way in Chromium, a browser and a mail client.

- **The document** opens with a cover (the wordmark, the accent stripe, the report name, the customer and its code, the period and the period it is compared with, the contents, the confidentiality line and who prepared it), then an executive summary: a one-line summary, up to six KPI tiles with the change against the previous period, a target and a sparkline where one exists, the remaining tiles in a compact row, the three lists *What went well*, *What needs attention* and *Next steps*, and two headline charts. The detail table follows, then the sections grouped into chapters, each with an intro line, charts of seven kinds (bar, horizontal bar, stacked bar, line, donut, heatmap, gauge), callouts and zebra tables with a totals row where the definition declares one, and an appendix with the definitions of every term used, data notes (the timezone of hour-of-day figures, row caps, sections with nothing to report, the SOC exclusion for staff without `soc:read`), the parameters and the run id. Tables print at most 100 rows in a plain document (the review pack uses `reports.print_rows`), a table with more than nine columns and more than four rows turns its section into landscape pages, and a document for one customer never repeats that customer in a column; the Excel workbook and the CSV always hold every row and column. Every page after the cover carries a running header (report and customer, period) and footer (confidentiality line, platform and generation time, "Page x of y") through `@page` margin boxes, which need Chromium 131 or later: the production image's Debian package qualifies; on an older host (`chromium --version`) the pages print without them and nothing else changes. To inspect a file by hand, `pdftoppm -png -r 60 file.pdf out` renders the pages and `pdftotext file.pdf -` extracts the text.
- **PDF** is produced by a Chromium binary in the container (`apps/api/src/lib/pdf.ts`): one headless process per document, `--print-to-pdf` on A4 with the document's own `@page` rules, at most one render at a time in the API process and a 60-second limit. The lookup takes `PDF_CHROMIUM_PATH` first, then the usual locations (`/usr/bin/chromium`, `/usr/bin/chromium-browser`, `/usr/bin/google-chrome`). The production image installs Chromium (Debian's package, with DejaVu and Liberation fonts) in its runtime stage and sets `PDF_CHROMIUM_PATH=/usr/bin/chromium`, so PDF output works out of the box; set the variable only when running outside the image. `GET /api/reports/definitions` returns `pdf: true` once a binary is found; the Reports page enables the buttons from that flag and a schedule in a PDF format is refused with a clear message while it is false. A render failure (a crash, the time limit) marks the run `failed` with the Chromium message in its error column and, on a schedule, counts as a failure for that target. Field visit reports (`POST /api/field/visits/:id/report`) are stored as PDF when Chromium is present and as printable HTML otherwise.
- **Excel** needs nothing extra (`exceljs`). The workbook has a Summary sheet (report, customer, period, the narrative line, the summary figures with their previous-period values, the insights and next steps, the recommendations, the parameters, a contents list), a Detail sheet with the main table, one sheet per section and a Charts sheet with the chart data (a heatmap as row, column, value triples so a pivot table can rebuild it); numbers, percentages and dates are typed cells, the header row is frozen and filtered, sheet names are cut to Excel's 31 characters and kept unique. CSV carries the tables and an Insights block.
- **Branding**: `platform.name` names the platform everywhere; `platform.logo_url` (an https URL or an inline `data:image/...` URI; anything else is ignored) replaces the bundled Progression wordmark on the cover and the masthead; `platform.brand_color` (a six-digit hex, the Progression navy by default) colours the headings, the cover title, the section rules and the Excel header rows; `platform.brand_accent` (the Progression red by default) colours the cover stripe and the section markers and is never used for text; `reports.confidentiality_line` is the footer line on every page with `{customer}` and `{platform}` replaced (a report without a customer prints "<platform> internal"); `reports.print_rows` caps the rows printed per table in review pack documents (10-500; the Excel workbook always holds every row). Reports flagged with a cover (the service review pack and PDF output of any report) open with the cover page.
- **Comparison, insights and narrative**: a report with a period runs a second time for the previous period of the same length (the whole previous calendar month for *Last month*) and every numeric tile gains a delta badge coloured by whether the move is good; snapshot reports (open tickets, asset register, CMDB inventory, contract expiry, software inventory, licence compliance, known errors) and the audit report are not compared, and a definition switches the comparison off with `compare: false`. Insights come from fixed rules over the figures (`apps/api/src/modules/reports/insights.ts`): a trend against the previous period, a figure against its target, a category holding 40% or more of a chart, the weakest and strongest category of a percentage chart, a spike in a time series, and a clean sheet when an exception list is empty; next steps are the pack's recommendations or one templated step per area that needs attention. When a provider is configured, the **Report insights and recommendations** switch on the AI page is on and `reports.narrative` is true, the assistant rephrases the summary and the three lists of HTML, PDF and Excel runs between the report's two transactions, never inside one; the model never supplies a figure: a sentence carrying a number the input does not hold is dropped and the rules' sentence stands. On-screen previews, CSV, Grady's `export_report` and runs with the switch off always carry the rules' wording; the audit record of a run says which (`narrative: rules` or `model`).
- **The service review pack** (`service_review_pack`, category Customers, portal-visible) is the monthly review for one customer. The scorecard judges every line On target, Watch or Needs attention: overall, resolution and response SLA compliance, breaches, MTTA, MTTR, first-contact resolution, reopen rate, backlog at period end, tickets opened and resolved, major incidents, customer satisfaction, open known errors, change success rate, entitlements over threshold, expiring asset cover, licence position, PM on time and, for staff, out-of-scope requests. The tiles carry deltas against the previous period and the chapters follow: Service levels (compliance by priority and metric, the gauge, met against breached, breached tickets), Demand and workload (volume by week, opened by type, the priority mix, the arrival heatmap by weekday and hour in the customer's timezone with the after-hours share, top services and categories, by site), Responsiveness (MTTA, MTTR, first-contact resolution and reopen rate by priority, backlog ageing and, for staff, resolution by engineer), Major incidents, Problems and known errors, Changes (the changes of the period, the success rate, failed or backed-out changes and, for staff, the CAB decisions), Customer satisfaction (by service, the rating distribution, the weekly trend, the lowest-rated tickets), Contracts and entitlements, Assets and software (expiring cover, licence positions), Field service and maintenance, for staff Out-of-scope work, and last the numbered recommendations with their evidence, drawn by fixed rules (breaches, major incidents, a reopen rate above 10%, first-contact resolution below 55%, a backlog that grew by a fifth, after-hours arrivals of 35% or more, open known errors, change success below 95%, low ratings, exhausted or warning entitlements, expiring cover, over-deployed or unlicensed titles, PM on time below 90%, out-of-scope work). A part the caller may not run (surveys, known errors, software, maintenance, field visits, CAB) is left out rather than refused, and a part whose definition is not registered on the installation is named in the appendix data notes ("Parts not available on this installation"). PDF tables are capped at `reports.print_rows` rows with a pointer to the Excel workbook, so a typical pack prints on 10 to 14 pages. The customer is required; portal users get their own organisation without the out-of-scope part, the engineer breakdown, the CAB decisions and any staff name column, and the confidentiality line names their organisation. A schedule in the **PDF + Excel** format produces both files on one run and attaches both to the delivery email, whose body opens with the narrative summary; "Save as schedule" from the Reports page prefills it.

## Known error database

A **known error** is a problem whose root cause is understood and whose workaround is written down. Engineers flag it on the problem record's **Problem analysis** tab (`problems:manage`): ticking *Known error* stamps the identification date and starts the entry's own lifecycle: `open` (workaround known, no fix under way), `fix_in_progress` (a change delivers the permanent fix), `resolved` (the fix is in) and `retired` (no longer relevant; retired entries leave the portal). The entry is the problem record itself (`problem_details`), so nothing is copied: the symptoms, workaround, root cause and permanent fix are the ones on the problem, and row-level security fences every read to the customers the person may see.

**Knowledge → Known errors** (`kedb:read`, held by every system role that reads knowledge articles; custom roles must be granted it by hand) lists every known error with a search over the title, symptoms, root cause, workaround, permanent fix and the customer wording, filters for status (Active, that is open or fix in progress, by default), customer, service, published to the portal and has a fix change, and tiles for open entries, fixes in progress, entries published to the portal and incidents linked in the last 30 days. The record page shows the workaround, the root cause and the permanent fix, the **fix change** (a change ticket of the same customer, set here or on the problem; when it is implemented the known error moves to resolved while `known_errors.resolve_on_fix` is on), the linked incidents with a picker to link more, the affected configuration items, the customer-facing wording and the problem's activity; the status moves (fix in progress, resolved, retire, back to open) sit in the overflow menu.

While an incident is raised (**Tickets → Create new** and the portal's new-ticket page) and on the incident record's Assist rail, the best matching known errors of the same customer are suggested from the title, boosted by the service and the configuration item and capped by `known_errors.suggest_limit`; **Link** on the rail creates the `problem_of` link, and a linked known error shows its workaround on the incident, appears under Related records as *Known error* and on the portal ticket as a *Known issue* card. The Problems tab of the ticket list has a *Known errors* tile and filter; the Knowledge overview, the NOC dashboard (open) and the customer home (published, with the latest entries) carry the figures; global search has a *Known error* type; the **Known error database** report (customer users get the published entries with the customer wording only) and three new columns on **Problem summary** (status, published, fix change) cover it in Reports.

**Publishing to the portal** (`kedb:publish`, held by the service, NOC and SOC managers) writes the customer-facing summary (what customers may notice) and workaround (what to do in the meantime) in a dialog; **Write with Grady** drafts both from the problem record when a provider is configured and the *Drafted customer wording for known errors* feature switch is on, and a deterministic draft that strips hostnames and addresses is used otherwise. The first publication sends `known_error.published` (email, in-app and WhatsApp for people who opted in; templates under Administration → Notifications) to the organisation's active portal users while `known_errors.notify_customers` is on; updating the wording later sends nothing. Customers (`portal:kedb`, both portal roles) see **Knowledge → Known errors** with the published entries of their own organisation only (title, summary, workaround, service, status and dates; never the internal workaround, root cause, fix change, engineer names or another organisation), a record page with *Still affected? Raise a ticket* and the suggestions while raising a ticket. *Withdraw from the portal* keeps the wording for a later publication. Everything is audited on the problem ticket (`known_error.update`, `known_error.publish`, `known_error.unpublish`, `known_error.resolve_on_fix`). Grady answers "is this a known issue" and "what is the workaround" through `known_errors`, `get_known_error` and `match_known_errors`, flags a problem with `mark_known_error` and publishes with `publish_known_error` (previewed and confirmed); in the portal the read tools return published entries only.

## Customer satisfaction surveys

When a ticket ends, the person who raised it is asked one question. The default policy (**Administration → Settings → Customer satisfaction**, the `surveys.*` keys) sends the survey when an incident or a service request is **resolved** (`surveys.send_on`; `closed` sends it at closure instead) and, while `surveys.resend_on_close` is on, sends it once more when the ticket closes at least a day later without an answer. A ticket closed straight from open (or reopened after a resolution and then closed) gets its survey at closure; a ticket that was skipped at resolution is not asked again at closure, and amending a resolution never re-sends a live survey. `surveys.sampling_pct` decides which share of eligible tickets is surveyed (the choice is stable per ticket), `surveys.fatigue_days` keeps one requester from being surveyed again within that many days, and `surveys.ticket_types` limits the types. The survey goes to the requester only when that person is a portal user or a contact with an email address or a WhatsApp number; a ticket raised by staff on a phone call without a contact is not surveyed, and the record says so (*Not sent: no customer recipient*). A reopen withdraws a pending survey and the next resolution issues a fresh one; an answered survey stands, a customer is never asked twice about one ticket.

The email (`ticket.survey_requested`, editable under Administration → Notifications, with a WhatsApp variant for people who opted in) carries the question and five one-click buttons. Each opens `/survey/<token>?rating=N`, a public page outside the application that needs no sign-in and names nothing but the respondent's own ticket number and title; the page records the rating through a request of its own once it has loaded, so link scanners that merely fetch the page record nothing. The token is random, stored hashed, valid for `surveys.expiry_days` (14 by default); an expired link reads *This survey has closed*, an unknown or withdrawn one *This link is not valid*, and a second answer is refused (*already rated*). A comment can be added once after the rating. Signed-in customers get the same prompt as a **How did we do?** card on the ticket in the portal (also reached from the in-app notification and from **My tickets → To rate**, an amber chip that counts the tickets waiting for a rating); a customer may rate any ticket that ended within the expiry window from the portal even when sampling skipped it. The `survey-sweep` job (`notifications` queue, every hour) sends one reminder after `surveys.reminder_days` (0 = none) and marks unanswered surveys expired.

A rating at or below `surveys.low_rating_threshold` (2 by default) sends `ticket.survey_low_rating` to the ticket's assignee, the team manager and the customer's account manager by email and in-app (the rule is seeded under Notification rules), with the rating and the comment. Everything is recorded on the ticket: *Satisfaction survey sent*, *Reminder sent*, *Customer rated this ticket N/5* in the activity stream, `survey.send` and `survey.answer` in the audit log.

Where the figures show: the ticket record's **Resolution information** carries the customer rating (stars, who answered, through which channel, when, and the comment) or the state of the survey, and holders of `surveys:manage` get **Send survey** in the overflow menu of an ended ticket without an answer (it bypasses sampling and fatigue). The ticket list has a **Rating** filter (rated, low, awaiting reply, not surveyed) and shows the stars on rated rows. **Reports → Customer satisfaction** (`surveys:read`) is the CSAT page: average rating, share satisfied (`surveys.satisfied_threshold`, 4 by default), response rate, responses and low ratings for a period, the weekly trend, a breakdown by customer, engineer, team or service, the rating distribution and every response with its comment, filterable by customer, engineer, team, service, rating and channel; the Export link runs the **Customer satisfaction responses** report. The Overview's management block carries a Customer satisfaction panel (average with its change against the previous period, satisfied share, responses, low ratings and the weekly average), the AMC dashboard the AMC figure, the engineer's own dashboard a *Customer feedback for you* panel, the customer home (portal and staff preview) a *Your satisfaction* tile and the tickets still to rate, and the customer record its 90-day figure. In Reports, **Customer satisfaction summary** and **Customer satisfaction responses** run to CSV, HTML, PDF and Excel and can be scheduled; the monthly service report gained a *Customer satisfaction* tile and the service review pack a scorecard line, a tile, a *Customer satisfaction by service* section, the lowest-rated tickets and a recommendation rule. Customer users see their own organisation's figures only, never engineer or team names; staff without `soc:read` never see the ratings of security tickets, the same fence as everywhere else.

**Administration → Workflow & automation → Satisfaction surveys** (`surveys:manage` or `admin:config`) shows the defaults and the overrides per customer or per contract: switch a customer off, change its sampling, timing, thresholds, ticket types, question or comment prompt; a contract override sits above the customer's, and every empty field inherits. Two permission keys: `surveys:read` (the page, the report and the dashboard figures; held by the service, NOC and SOC managers, the service desk, contract administrators, management and auditors) and `surveys:manage` (policies and the manual send; the ITSM administrator, service managers and account managers). Grady answers "what is our CSAT this month" and "which tickets got a poor rating" with `csat_summary` and `csat_low_ratings`, re-sends a survey with `send_survey` (confirmed), and lets a portal user rate a ticket in the conversation with `rate_ticket`.

## Task boards

**Tickets → Task boards** (`/tickets/boards`, anyone with `tickets:read`) shows the work as kanban lanes instead of a list. Two boards share the page: the **ticket board** (incidents, requests, problems and changes) and the **task board** (the tasks on those tickets). The **Scope** switch picks whose work is shown: *My board* (tickets or tasks assigned to the person), *Team* (a team the person belongs to; people with `oncall:manage` or `tenant:all` may pick any team), *Engineer* (one colleague) or *Everything* (all the person may see). The **Lanes** switch lays the cards out by **status** (one lane per status that applies to the ticket types in view, ordered as the option list is; Closed and Cancelled only with *Show closed*; statuses of a single type with no card in them are hidden unless *Show empty lanes* is on) or by **assignee** (one lane per engineer in scope, Unassigned first; a team's members all get a lane). The filter bar narrows the cards by search, type, customer and priority (tickets) or search, customer and due date (tasks; *Today* and *This week* follow the person's own time zone from their profile). The board shows the most recently active cards up to `boards.card_limit` (300 by default) and says so when it truncated; the lane figures stay exact.

**Moving a card** performs the record's own transition through the same routes the ticket page uses, with the same permission: a status lane calls the status change (`tickets:update`; Resolved, Closed and Cancelled need `tickets:resolve` and open the usual dialog for the resolution notes, the closure code and the comment first), an assignee lane calls the assignment (`tickets:assign`), a task lane updates the task (`tickets:update` on the parent ticket). While a card is dragged, the lanes it may not land in are greyed out: a status that does not apply to the card's type, or an action the person lacks the permission for. A drop the server refuses (a missing permission, a status that does not apply, resolution notes missing) puts the card back where it was and shows the server's message in a toast, so the board can never do what the record page would refuse. Every card has a menu with the quick actions (open, assign to me, move to a lane, resolve, add a task, watch; mark a task done, reopen, delete) and **Move to…** is the keyboard and touch path to the same moves. On a phone the board shows one lane at a time, chosen from a list, and moves go through the card menu.

**WIP indicators** mark overload without blocking anything: each lane header shows its card count against a limit, amber at the limit and red over it. The limit per engineer (on the assignee lanes) is the platform setting `boards.wip_default_limit` (8 open tickets by default; 0 switches the indicator off); a person can also set a limit of their own on any lane through the **Lanes…** button, which also reorders, hides and collapses lanes. The three settings live under **Administration → Settings → Task boards** and Grady may change them with confirmation.

The **panel** beside the board (Handover, Notes, Both or Hidden) shows two things. The **handover** card reads the shift handover module for the chosen team: the shift running now and the one after it, the latest published note (its *Watch first* section, with a link to the full note), who acknowledged it, and an **Acknowledge** button for whoever takes over (`handover:write`, a member of the team or `oncall:manage`, never the author); writing a handover stays on **Operations → Shift handover**. The **sticky notes** card holds the person's own notes for the shift: a one-line composer (Enter adds), a colour, pin, done and delete. Notes are personal: only their author can read or change them (the service filters by author and the `board_notes` table carries a per-user row-level policy), a note written on a team board stays with that board, and done notes are removed `boards.note_retention_days` (30 by default) after they were marked done by the `board-notes-purge` job (`maintenance` queue, nightly at 03:40); editing or pinning a done note does not restart that clock.

The board layout is remembered per person in their profile preferences (the board, scope, team, engineer, lanes, filters, lane order, hidden and collapsed lanes, personal WIP limits, the panel and the handover team), saved shortly after each change and restored on the next visit; a link that carries board parameters (from Grady, the engineer dashboard's *My board* link or a colleague) wins over the saved layout for that visit. Customer users never reach the boards: the page is staff-only and every `/boards/*` route refuses them. Grady answers "what's on my board", "how loaded is the NOC" and "who is over their WIP limit" with `my_board` and `team_board`, including whether the latest handover was acknowledged, and adds a sticky note on request with `add_board_note`.

## Software asset management

**Assets → Software** (`/assets/software`, holders of `software:read`; changes need `software:manage`) tracks what software is installed at each customer and whether it is licensed. The module has its own strip under the Assets strip: **Overview**, **Titles**, **Installations**, **Licences**, **Compliance** and **Renewals**. The customer picker on the overview scopes every tile; the list pages carry the customer as a filter.

- **Titles** are the shared catalogue: one row per publisher, product and version family (Microsoft · Office LTSC · 2021), with a category from the **Software categories** option list (Administration → Option lists → Assets) and a licence model (per device, per user, per core, subscription, perpetual) that sets the default metric and term of new licences. Titles are not owned by a customer; the import adds unknown ones automatically while `software.import_creates_products` is on. A title with installations or licences cannot be deleted; deactivate it instead and it keeps its history while refusing new licences.
- **Installations** record one title on one host for one customer: a configuration item, an asset, a plain host name for machines not in the CMDB yet, or only a user for named-user subscriptions. Record them by hand (**Record installation**, with the CI picker; the linked asset or CI is filled in from the other half of the pair), or import an inventory export with **Import CSV**: download the template first; the columns are `publisher`, `product`, `versionFamily`, `version`, `edition`, `hostname`, `assetTag`, `serialNumber`, `user`, `cores`, `installedAt`, `source`, `notes`. A row is matched to a host by asset tag, then serial number, then host name against the customer's CIs and assets; a row that matches an installation already recorded updates its version, edition, cores, user and last-seen time instead of duplicating it. Imported and discovered installations that are not seen again for `software.stale_install_days` (45 by default) are flagged stale on every list and still count towards the position (the conservative reading); records entered by hand never go stale. **Export CSV** writes the filtered list.
- **Licences** are entitlements per customer: a name, the title, the metric (devices, named users, cores, or a site licence with no limit), the term (subscription or perpetual), the seats, start and end dates, the renewal date and auto-renew flag, the contract it sits under, the cost, currency, vendor, purchase order, invoice, licence key (shown masked on the record), owner and notes. Proof of purchase (invoice, agreement, certificate) is attached on the licence record's **Proof of purchase** tab; those files never reach the portal. **Renew** on a licence records the next term as a new licence linked from the old one: the old licence stays in force until its own end date and reads *Renewed* afterwards, so the title is never unlicensed between recording the renewal and the new term starting; a licence can be renewed once, and the next term must start after the current one ends (shorten the end date first for an early renewal). Editing a licence's start or end date resets its notification milestones, so the daily job notifies again for the new term. Deleting a licence removes its proof-of-purchase files with it.
- **Compliance** is computed live, never stored: for every customer and title pair the installed count on live hosts (retired CIs and retired or disposed assets are left out; devices for per-device, distinct users for per-user, the sum of cores for per-core) is set against the seats of the licences in term today. The position is **compliant**, **under-deployed** (fewer than `software.unused_seat_pct` percent of the seats in use, 80 by default), **over-deployed** (more installed than licensed), **unlicensed** (installed with no licence in term) or **unlimited** (a site licence). A renewed licence still in term counts until its end date; its successor counts from its own start date. The tiles on the Compliance page narrow the list to one position; a row opens the title record with that customer preselected.
- **Renewals** lists the licences ending or renewing within 30, 90, 180 or 365 days, expired first, and never a renewed one. The `software-daily` job (`maintenance` queue, 06:30 every day) sends `licence.expiring` once per threshold in `software.licence_notice_days` (90, 30 and 7 days before the end date by default), `licence.expired` once the day after, and `software.over_deployed` once per title and customer while the position is over-deployed or unlicensed (the milestone is cleared when the position recovers, so a relapse notifies again). Recipients follow the contract rule: the customer's account manager, the licence owner and the active holders of `contract_admin` and `service_manager` (plus `cmdb_admin` for over-deployment); the templates are under Administration → Notifications.
- **Asset and CI records** carry a **Software** tab with the installations on that host; the **Assets overview** shows a *Software and licences* panel for holders of `software:read`.
- **Reports**: *Software inventory* (installations with host, user, version, source and stale flag; by publisher and category) and *Licence compliance* (every position with the licences behind it; the cost column appears for staff only). Both are portal-visible for customer users who hold `portal:software` and pinned to the customer there.
- **Customers** with the `portal:software` permission (customer administrators by default; grant it to customer users under Administration → Roles) see **Assets → Software** in the portal: the titles in use with their position, the licences (name, seats, term, renewal date, contract and status) and the installations (title, version, host, user, last seen). Cost, currency, vendor, purchase orders, invoices, licence keys, owners and notes never leave the staff side.
- **Grady** answers "which titles are over-deployed at a customer", "what renews this quarter", "how many installs of a title do we have" and "show me licence X" with `software_inventory`, `software_compliance`, `licence_renewals` and `get_licence`, and records a licence or an installation after a preview with `record_licence` and `record_installation`; customer administrators get the same four read tools pinned to their organisation.

The four settings live under **Administration → Settings → Software assets** and Grady may change them with confirmation.

## Custom reports

**Reports → Report builder** (`/reports/builder`, holders of `reports:build`: the ITSM administrator, the service, NOC, SOC and account managers, contract administrators, management and auditors) builds a report in the browser without writing any SQL: pick an entity, tick columns, add filters, group and aggregate, sort, choose the period field and the customer scope, preview, then save. A saved report is an ordinary catalogue entry with the key `custom:<id>`: it runs from **Reports → Catalogue** under *Custom reports*, downloads as CSV, HTML, PDF and Excel, and is scheduled like a built-in report (the schedule form lists it by name). The builder page opens with *Your custom reports* (the ones the person may see, with run counts and the last run; a row opens the report, Run jumps to the catalogue, Duplicate makes a private copy) above the configuration card and the live preview; a *Describe it* box turns one sentence into a draft when the assistant is on.

- **Entities**: tickets, changes, problems, SLA clocks, time entries, field visits, assets, configuration items, contracts, entitlements, surveys and software installations. Every field is an entry of a fixed catalogue (`apps/api/src/modules/reports/builder/catalog.ts`): nothing typed in the browser reaches the database as SQL, values travel as bound parameters, and an unknown field, operator, sort key or aggregate is refused with a message that names it. An entity also needs its own read permission (`tickets:read`, `assets:read`, `cmdb:read`, `field:read`, `contracts:read`, `surveys:read`, `software:read`); a tile the person may not use says which one. SOC tickets stay hidden from people without `soc:read` through every ticket-based entity, including time entries, SLA clocks and surveys.
- **Grouping**: one or two group fields with count, total, average, lowest or highest per group; a grouped report carries one summary tile per aggregate and a bar or line chart of the first group field. The aggregate columns are named `count` or `<function>_<field>` (for example `avg_resolution_minutes`) in sort keys, chart series and CSV headers; the label the person types is only the heading.
- **Scope and period**: a report is either fixed to one customer (every run and schedule then uses that customer; a schedule for a different customer or the per-customer fan-out is refused with "This report is fixed to <customer>") or takes the customer at run time like a built-in. The period field (created, resolved, scheduled start, warranty end and so on) and the default period behave like every other report's date range. A report with neither a period field nor a fixed customer reads the whole entity; the builder says so and the row cap still applies.
- **Limits**: `reports.builder.max_rows` (10,000 by default; when a run is capped the true total is still reported), `reports.builder.preview_rows` (500) and `reports.builder.statement_timeout_ms` (20,000). The limit covers one run as a whole: the row query first and, only when the rows were capped, the count of matching rows with whatever time is left (a second at least). A run over the time limit fails with "This report took longer than N seconds; add a filter or shorten the period" and leaves the other reports of the same worker run unaffected. Lowering `reports.builder.max_rows` below the row limit saved in a report clamps that report at run time; it is not refused. The three settings sit under **Administration → Settings → Reports** and Grady may change them with confirmation.
- **Sharing**: *Only me* (the owner and report managers see it), *Shared* with staff roles and teams (who must also hold the entity's permission), and *Visible in the customer portal*, offered only for portal-capable entities when every field used is portal-safe (the toggle names the internal fields that block it; the server checks again when the report is saved and every time it runs). A published report appears in the customer's **Reports** catalogue pinned to their organisation; the portal never shows the builder, owner names, sharing lists or filter values (a portal user sees which fields a published report filters on, not the values). Staff see the filters in words, with the records named (customers, priorities, people) rather than their ids, on the run card, in *Your custom reports* and in the audit trail. The owner, report managers and anyone the report is shared with who also holds `reports:build` may edit it (the pencil in the catalogue picker and *Edit in builder* on the run card; the run card also names the roles and teams a shared report reaches); only the owner and `reports:manage` holders may delete, retire or restore it. A report manager without `reports:build` can still open the editor on anyone's report (the catalogue and the preview accept `reports:manage` too), while saving a new report and duplicating need `reports:build`. Fixing a report to one customer is refused while a schedule runs it for another customer or for every customer.
- **Deleting retires**: the definition leaves the catalogue and the picker, its past runs stay in **History** under the `custom:<id>` key for the people who could see the report, and a report manager can tick *Include retired* in *Your custom reports* on the builder page to list them and press *Restore* (the API: `GET /reports/custom?includeInactive=true` and a patch of `isActive: true`; retiring through a patch follows the same rules as the delete). A report with schedules cannot be retired until they are removed.
- **Audit**: `report_definition` entries for `create`, `update` (the changed fields and the new plain-English summary), `delete` and every `preview`, so "who looked at what" has an answer.
- **Grady**: `report_catalog` lists the entities and fields; `build_report` proposes a saved report after a preview that shows the compiled definition and a sample of rows; `run_report`, `export_report` and `schedule_report` accept custom reports by name or key. The *Describe it* box calls `POST /reports/builder/suggest` behind the **Report builder suggestions** switch on the AI assistant page; with the switch off, or without a provider, it fills a basic layout from the words in the sentence (the entity, a group field after "by", the period) and says so.

## Notification preferences

Three layers decide what a person receives for an event. The **notification rule** (Administration → Notifications → Notification rules) is the ceiling: it names the recipients and the channels an event may use at all. The **notification defaults** (Administration → Notifications → Notification defaults, `admin:config`) say, for each of fifteen categories and for email and WhatsApp, whether the channel is on by default and whether it is locked; a locked channel cannot be switched off by anyone of that audience, and a lock is refused while the default is off. The seeded locks are email on SLA warnings and breaches, on escalations and major incidents and on approval requests and decisions, and both email and WhatsApp on on-call pages; unlocking a channel on on-call pages lets engineers mute pages on it (email and in-app still arrive). The daily briefing row is the one exception: each person chooses it on their Daily briefing card and the defaults page only shows it. Categories are defined by the platform: rows cannot be added or deleted, and a change of a default never flips a choice a person already made. The **person's own matrix** (Profile → Notifications; customers reach the same page under Account → Profile & notifications) removes channels per category, one checkbox per cell saved on click; a locked cell shows a lock; in-app notifications are always on, and the account messages (welcome, password reset, verification code) always go out. WhatsApp additionally needs the person's mobile number and opt-in on the same card, so a lock never sends WhatsApp to someone who did not opt in, and the WhatsApp column stays disabled with the reason until both are there (or while WhatsApp is not set up on the platform). Staff see fourteen rows (assignments and ticket updates, comments and replies, resolution and closure, SLA warnings and breaches, escalations and major incidents, on-call pages, approval requests and decisions, changes and CAB, field visits and maintenance, shift handover, daily briefing, contracts and licences, customer feedback, scheduled reports); customers see ten rows with customer wording (ticket updates, replies from the service desk, resolution and closure, major incident updates, approvals, planned changes, visits and maintenance, satisfaction surveys, known issues, scheduled reports) and never a row or a sentence about escalations, sentiment, overdue updates or staff workload. Contacts without a portal account have no matrix: the rule and the contact's opt-in decide. Only the cells a person set are stored (`users.preferences.notifications`). Dispatch applies the three layers for every recipient with an account the moment a notification is queued and fills in the recipient's number and opt-in when the sending module did not pass them, so field visit and maintenance events reach WhatsApp for opted-in people when their rule lists the channel; the worker applies a changed default within thirty seconds. Scheduled report deliveries honour the Scheduled reports row for user recipients; explicit addresses are unaffected. Every change of a default is in the audit log as `notification_category` / `update` with the category key, and a person's change as `notification_preferences.update`. Grady reads and changes one's own matrix by sentence (`my_notification_preferences`, `set_notification_preference`); an administrator's "lock email for approvals" is `upsert_config` on `notification-categories`.

**Verifying a number.** *Verify number* on the profile sends a six-digit code to the number over WhatsApp (event `user.phone_verification`, template group `user`, which falls back to the default template; an authentication-category template may be mapped for it on the WhatsApp page) and opens a dialog for the code. The code lives ten minutes, a person may request three an hour and has five attempts; typing it sets `users.whatsapp_verified_at` and shows a Verified badge (it does not change the WhatsApp opt-in, which stays the person's consent to notifications). Changing or removing the number, on the profile or by an administrator on the Users pages, clears the verification (audited as `phone.verification_cleared`); *Remove number* on the card clears the number, the opt-in and the verification in one step. A number that another account has already verified is refused (one account per verified number); an administrator frees it by changing the other account's number. Notifications do not require verification; chatting with Grady on WhatsApp will. The sent text, code included, stays in the outbox for the retention period like any other message; it is useless without the person's session and void after ten minutes. The Users pages show whether a number is verified.

**A channel is missing.** Check in this order: the rule lists the channel; the default for the category is on (or locked); the person has not switched it off on their profile; for WhatsApp the person has a number and the opt-in; then Administration → Notification outbox for the row and its delivery state. ## AI assistant troubleshooting

The assistant uses the provider set by `AI_PROVIDER` (`anthropic`, `openai_compatible` or `none`), the model in `AI_MODEL` and, for OpenAI-compatible endpoints, `OPENAI_COMPATIBLE_BASE_URL` plus `OPENAI_COMPATIBLE_API_KEY`. Environment variables are read when the container starts, so run `docker compose up -d` after changing `.env`.

Setting only `OPENAI_API_KEY=sk-...` is enough: the provider, `https://api.openai.com/v1` and `gpt-4o-mini` are inferred and the choice is logged at startup as `AI assistant enabled` (with notes explaining any inferred value). The explicit combination is:

```
AI_PROVIDER=openai_compatible
OPENAI_COMPATIBLE_BASE_URL=https://api.openai.com/v1
OPENAI_COMPATIBLE_API_KEY=sk-...
AI_MODEL=gpt-4o-mini
```

Check the configuration from the product first: **Administration → AI assistant → Test connection** sends a one-line prompt and shows the latency, or the exact status and message the provider returned. The same page holds the kill switch, the feature switches, the autonomy mode (`ai.autonomy`: confirm every change, or auto-apply low-risk internal writes), the reasoning effort, the daily token budget per person (`ai.daily_token_budget`, 0 = unlimited), the reply timeout (`ai.turn_timeout_seconds`), the conversation retention (`ai.conversation_retention_days`; the nightly `conversation-purge` job on the `ai` queue deletes older conversations, 0 keeps them forever) and the usage report (replies, tokens and cache share, tool calls, feedback, fenced and denied events, per-tool counts). The same information is logged by the API as `AI endpoint error` with the provider, model and endpoint (never the key).

From the Docker host:

```bash
docker compose exec app env | grep -E '^(AI_|OPENAI_)'          # what the container actually sees
docker compose logs app --tail 200 | grep -i "AI endpoint"       # upstream status and message
curl https://api.openai.com/v1/chat/completions \                # the same call outside the platform
  -H "authorization: Bearer $OPENAI_COMPATIBLE_API_KEY" -H 'content-type: application/json' \
  -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"ping"}],"max_tokens":16}'
```

Common causes:

| Symptom | Cause | Fix |
|---|---|---|
| HTTP 400 `Unsupported parameter: max_tokens` | Newer OpenAI models only accept `max_completion_tokens` | Handled automatically (the app retries in the modern shape); upgrade if you see it in the logs |
| HTTP 404 `model_not_found` / `The model ... does not exist` | `AI_MODEL` is not a model of that provider (default is a Claude id) | Set `AI_MODEL` to a model the endpoint serves |
| HTTP 401 `Incorrect API key` | Wrong or truncated key, or the key is in the wrong variable | Put the key in `OPENAI_COMPATIBLE_API_KEY` (or `ANTHROPIC_API_KEY` for Anthropic) |
| HTTP 404 on the endpoint itself | Base URL missing `/v1` or pointing at a UI page | Use the API base; `/chat/completions` is appended by the app and stripped if pasted |
| "could not be reached" | Container cannot resolve or reach the host (proxy, firewall, Ollama not published) | Test with `docker compose exec app wget -qO- <base url>/models` and fix networking |
| Assistant says it is not configured | `AI_PROVIDER` is `none` or the matching key / URL is empty | Set the variables and restart |
| Browser shows `POST /api/ai/chat` → 400 `Request validation failed` | Versions before this release rejected a new conversation from the panel (`conversationId: null`); nothing reached the provider | Upgrade (`docker compose build && docker compose up -d`) |

## Dashboards

Every staff member lands on the **Overview** (`/`). It opens with a greeting and the shift running now in one of the person's teams (from the shift rotas under Operations → Shift handover), then **My day** (assigned to me, breached, at risk, resolved today, approvals waiting, due today, and my queue by type), the **Announcements** aimed at staff, **Upcoming** work today and tomorrow (site visits, maintenance occurrences, CAB meetings and change windows, each under its own permission or limited to the person's own work) and the **Operations** cards: one per dashboard the person may open (Network operations, Security operations, AMC & field service) showing that dashboard's own tile numbers with an *Open dashboard* link. People who read tickets also get the **Service desk** block for the period: five tiles (open, breached, unassigned, resolved, SLA compliance; all but Unassigned carry the change against the previous period and a sparkline, Unassigned being a live count with no history behind it), the ticket flow per day (flow, breaches or compliance), open tickets by type, when tickets arrive (a weekday-by-hour heatmap of the last seven days, or the whole period's pattern), the backlog by age with the breached share, who carries the load (by team, engineer, service, customer or category), changes (open now and the outcome of those that ended) and response by priority (opened, resolved, first response, resolution, first-contact resolution, reopens). Holders of `dashboards:management` also get the **Management** block: account counts, customers that need attention, customer satisfaction, expiring contracts and entitlements near their limit.

The dedicated dashboards are pages of their own, listed in the strip under the hero and as the Dashboards modules in the navigator: **Network operations** (`dashboards:noc`; a Team control in the hero narrows every panel to one NOC team), **Security operations** (`dashboards:soc` and `soc:read`), **AMC & field service** (`dashboards:amc`) and **My work** (everyone). An old `/?view=noc` link redirects to the page, keeping the period and the scope.

Every dashboard filters the same way. The **Period** (7, 30 or 90 days) and the **Scope** (one customer or all) in the hero apply to every panel; the line under the strip says what is applied ("Showing All customers · last 30 days (8 Sep – 7 Oct)"), and the strip keeps them while moving between dashboards. The small control in a panel's header (All open / Breached on the ageing chart, Last 7 days / Pattern on the heatmap, Category / Team / Service on the load panel, and so on) changes that panel only, never a tile or another panel, and is kept in the URL so a view can be bookmarked. Nothing else on a dashboard filters the dashboard: every tile, donut slice, bar, heatmap cell, breakdown row and strip number is a link that opens the ticket list with exactly the conditions it was counted with (customer scope, domain, team, type, SLA state, the period or the hour as a created or resolved range), shown as a breadcrumb on the list, so the list's count equals the number that was clicked. "Breached" means an SLA clock the engine has flagged, "at risk" a running clock the engine has warned on, everywhere. A figure with no list behind it (due today, a percentage, a duration, an event count, a change outcome) is shown as a plain number. Grady's `dashboard_kpis` reads the same payloads and links to the same pages.

## Who sees what

Permissions decide what a user may do; **navigation areas** decide what their navigator shows. Each role carries a list of areas (Tickets, Customers, Contracts & scope, Service catalog, Teams, Assets, CMDB, Discovery, Monitoring & SIEM, Field service, Preventive maintenance, Knowledge, Reports). The navigator shows an application only when the user holds a permission for it **and** one of their roles lists its area; roles with no areas configured show everything their permissions allow. Administrators always see everything. Grady's replies on WhatsApp follow the same rules: a person's phone gets exactly what their own session would get, and a portal user's phone is fenced to their organisation.

The navigator groups applications into six sections, each a collapsible heading: **Insight** (Dashboards: the Overview and one module per dedicated dashboard, Reports), **Service desk** (Tickets with My approvals and Task boards, Knowledge with its articles and the known error database), **Service operations** (Operations: major incidents, on-call, announcements, shift handover; Changes: all changes, change calendar, CAB; Field service; Teams), **Accounts** (Customers, Contracts & scope, Service catalog), **Infrastructure** (Configuration (CMDB) with Discovery and Monitoring & SIEM, Assets) and **System** (Administration). An application expands into its modules when at least two are visible to the person; the *Filter navigator* box searches applications and modules and ignores collapsed sections; the collapsed rail (⌘B / Ctrl+B) shows one icon per application with a tooltip. Collapsing a section is remembered per browser, and the application you are on is always shown even inside a collapsed section. Monitoring & SIEM is reached from Configuration (CMDB) → Monitoring & SIEM by the NOC, SOC and CMDB roles and from Administration → System by administrators (the old `/integrations` and `/discovery` links redirect). A custom role that may only view integration events reaches the page through the CMDB when it also holds CMDB read access and, if it lists navigation areas, the Monitoring & SIEM area; a role that may manage integrations sees Administration instead, and the page always opens by its direct link. Record pages share one layout: breadcrumb trail and number/title in the header with at most two primary actions (the rest under "…"), a two-column field form, related lists as tabs, and an activity stream in the right rail.

The ticket record follows the ServiceNow incident form, top to bottom: the header (number, title, state and priority controls, scope, two primary actions) with an at-a-glance strip (assigned to, age, first response, next SLA target, due, reopens); an attention strip for staff; **Details** in two columns (left: customer, site, requester, service, contract, configuration item, asset, category and subcategory, tags; right: source, opened, status, impact, urgency, priority, team, assigned to, due); **Description** with the catalog form when the ticket came from the catalog; **Attachments**; **Resolution information** once there is any; **Related records** (parent and typed links); then the related lists as tabs (problem analysis or change plan, approvals, tasks, affected CIs and assets, SLA targets, time worked, linked tickets). The right rail holds the activity stream with the composer on top, the context cards and the assistant. The portal ticket uses the same order with customer wording (Details, Resolution, Description, Request details, Attachments) and a conversation rail.

Files can be attached while creating a ticket (staff and portal: pick, drop or paste a screenshot into the description; they are uploaded to the new ticket right after it is created) and while replying (the composer's paperclip, a drop or a paste). A note's files follow its audience: a reply's files are visible to the customer, a work note's stay internal; portal uploads are always visible to the customer's organisation. Files are uploaded before the note is posted and the note names them, so the activity stream and the e-mail copy record what was attached.

Every major application opens on an **Overview** and offers its modules in a strip under the page header, like the CMDB: Assets (Overview, Inventory, Warranty & AMC, Lifecycle, Software, with the Software module's own strip: Overview, Titles, Installations, Licences, Compliance, Renewals), Customers (Overview, Accounts), Contracts & scope (Overview, Contracts, Entitlements, Service levels), Field service (Overview, Visits, Calendar, Preventive maintenance), Knowledge (Overview, Articles, Known errors, Categories), Operations (Major incidents, On-call, Announcements, Handover), Changes (Change calendar, CAB, Change catalog), Reports (Catalogue, Report builder, Customer satisfaction); in the portal Service status (Status, Planned changes), Assets (Overview, Inventory, Warranty & AMC, Software), Services & contracts (Services, Service levels, Contracts), Maintenance & visits (Upcoming, History) and Knowledge (Overview, Articles, Known errors). The strips mirror the navigator's modules entry for entry; a strip with a single visible entry is not shown. Tickets stay a single list plus the **Task boards** page (kanban lanes over the same tickets and their tasks); staff with approval rights get a **My approvals** inbox under Tickets, and approval workflows run their steps in order.

Every list page has the same shape: a horizontal filter bar on top (a search box and one pill per filter; a pill opens a small panel with its options, counts, select, date range or toggle, and shows the chosen value on itself) and the results underneath. Under the bar the conditions in effect read as a breadcrumb, the way a ServiceNow list spells out its filter: a root chip for the default view ("All open" on Tickets), then one removable chip per condition in the order it was applied, and a count line such as "1–25 of 148 open incidents"; clicking the root chip returns to the default view. The bar sits on its own toolbar surface so filters never read as data. Stat tiles on a list page toggle one condition in place and show a ring; their figures are counted over the scope above them without the status chips or the tile toggles, so clicking one never changes another and the page never scrolls. On overview pages and dashboards a tile is a link that opens the list with the exact conditions its number was counted with (customer scope, domain, type, SLA state, and the period as a created or resolved date range), so the list's count equals the tile. "Breached" means an SLA the engine has flagged (the sweep runs every minute) and "at risk" a running clock the engine has warned on, on the list, every dashboard and the reports alike. Dashboards carry their interactive filters (period, customer scope and, on Network operations, the team) in the hero's filter row with a scope line that says what is applied, and one to three local controls in a chart's header, which change only that chart and are kept in the URL. Filter state lives in the URL, so a filtered view can be bookmarked or shared, and on Tickets it can be saved as a view that appears as a pill. The rules are written down in docs/DESIGN.md and checked by `npm run lint:ui`.

The configuration pages under Administration (option lists, custom fields, the service catalog, SLA policies, calendars, rules, workflows, change templates, notification rules and templates, the outbox, surveys, users, roles, teams, API keys, the WhatsApp inbound log, the audit log) find a row the same way: a search box over the page's own columns (a name, a key, a description, and what belongs to the row, such as a team's members, a service's line or a rule's recipients), one pill per filter (domain, type, channel, customer, status), an *Include inactive* switch where entries can be switched off (an entry that is off, or a blackout window that has ended, stays out of the view until the switch is on), the conditions as a breadcrumb with a "12 of 48" count, and paging at 50 rows. The state is in the URL, so a filtered page can be bookmarked, sent to a colleague or opened by Grady, and the back button returns to the previous view. Users and the audit log search on the server behind the same bar. Entries ordered with Move up and Move down (option lists, custom fields, CI types, assignment and escalation rules, risk questions) move past the entry shown next to them, so an inactive entry hidden from the view keeps its place; the arrows wait until the search and the pills are cleared.

System roles ship with sensible areas: a NOC engineer sees Dashboards, Tickets, Knowledge, Operations, Changes, Teams and the CMDB with discovery and monitoring; a field engineer sees Dashboards, Tickets, Knowledge, Operations, Changes, Field service, Teams and Assets; account managers see Dashboards, Reports, Tickets, Teams, Customers, Contracts & scope and the Service catalog. Adjust them under **Administration → Roles → Navigation areas**; the change applies at the next page load. The administration area is grouped the same way: Operating model, Service levels, Workflow & automation, Change management, CMDB model, Notifications, Access, System.

Three permission keys guard the known error database, none of which a custom role receives automatically. `kedb:read` opens Knowledge → Known errors and the matches on incidents (every system role that reads knowledge articles holds it). `kedb:publish` publishes, updates and withdraws the customer-facing wording (the ITSM administrator and the service, NOC and SOC managers). `portal:kedb` shows the published entries to a customer organisation in the portal (both customer roles).

Software asset management adds `software:read` (Assets → Software and its six modules; every system role that works with assets, contracts or the service desk holds it) and `software:manage` (titles, installations, licences, CSV import; the service manager, engineers, CMDB and contract administrators), both under the Assets navigation area, and `portal:software`, which shows the portal's Assets → Software page to a customer organisation (customer administrators by default).

`reports:build` opens the report builder; a custom report is seen by its owner, by the roles and teams it is shared with (who must also hold the entity's read permission), by `reports:manage` holders, and, when published, by the portal users of its customer.

The Reports application now lists a **Customer satisfaction** module next to the catalogue for holders of `surveys:read`; customers rate a resolved ticket from the portal (the card on the ticket and the **To rate** chip) or from the one-click links in the email, without signing in.

### Customer data isolation

A customer (portal) user is bound to exactly one organisation, and that binding is enforced in four layers that do not depend on each other:

1. **Database.** Every tenant table carries `customer_id` and has a forced row-level-security policy; the API sets the tenant context on every transaction (`app.customer_ids`), so a query that forgets a predicate still returns only that organisation's rows.
2. **Service layer.** List and lookup functions add the explicit `customer_id = <own customer>` predicate for portal users (tickets, search, knowledge, contracts, entitlements, SLA figures, maintenance), and a portal user asking for another customer by name or code is answered with their own data.
3. **Assistant (Grady).** Customer users are offered only the self-service tools (every one scoped to their own organisation by the service layer); the operating context names the organisation and the rules instruct the model to answer for it only; the worked examples use placeholder names that exist nowhere; every tool result is passed through a *tenant fence* that removes any record naming another organisation before the model sees it (a removal is logged and audited as `ai.tenant_fence`; under normal operation the count is always zero); the reply may only name tickets and link records the conversation has shown (`ai.answer_fence`); navigation is validated against the portal's pages; conversations are stored under the organisation and cannot be continued by the same account from another one.
4. **Browser.** The web client drops everything it cached for one person when another signs in, including the assistant's screen context.

`apps/api/test/ai-isolation.test.ts` exercises every assistant tool a portal user can reach with inputs that ask for a different customer and asserts that only the user's own organisation comes back.

### Customer replies on waiting tickets

A ticket in **Pending Customer** is the service desk waiting on the customer. When the customer answers (a portal comment, or a comment added through the assistant), the ticket returns to the working status for its type (Incident → In progress, Request → In fulfilment), the SLA clocks resume with the paused time credited, the timeline shows "Customer replied · back with the service desk", and the ticket leaves the customer's "Awaiting your reply" list. An engineer's own comment on a waiting ticket does not change its status.
